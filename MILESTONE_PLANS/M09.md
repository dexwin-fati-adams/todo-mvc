Certainty Checks
What comes into the system?
A status value from the query string: all, active, or completed. If left out, it defaults to all.
How will it be checked?
The FilterQuerySchema (Zod) in contracts checks that status is exactly one of the three allowed values, appears at most once, and that no other unknown query fields are sent. This is the single place that decides what's allowed, so the route, service, and repository all rely on it instead of re-checking the value themselves.
What will the operation return when it succeeds?
200, with a list of todos, filtered by status. Same shape as M08, just fewer or more items depending on the filter.
What expected failures can happen?
None. Bad input is rejected before it reaches the business logic (see Expected Failures).
How will each expected failure be represented?
Not applicable
Where will the route, business rules, and database work live?
The allowed status values and their validation live in contracts (todo.contracts.ts), shared by every layer. Route: todo.routes.ts. Business rules: todo.service.ts. Database work: todo.repository.ts.
What tests will you write before implementation?
A repository test that checks status=all, status=active, and status=completed each return the correct todos.
How will you prove the whole operation works through its real boundaries?
Run the repository test against the real test database, not a mock, so the actual SQL query is exercised.
Does this change multiple records or call another system?
No

Not applicable. This milestone is backend only.

Implementation Steps
●      In contracts: define the allowed status values once (a Filter type), and a schema (FilterQuerySchema) that checks incoming query strings against those values, with all as the default
●      In the repository: add a findAll function that takes a status and uses it to build the right database query — one branch per status, checked exhaustively so a new status can't be forgotten
●      Write a test for the repository function to confirm it filters correctly
●      In the service: update the function that builds the todo list so it takes the same status type from contracts and passes it straight through to the repository
●      In the route: parse the incoming query string with FilterQuerySchema, and pass the validated status into the service
