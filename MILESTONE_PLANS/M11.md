Objective
Add title search without adding pagination.

Included
●      How the search text is cleaned up before use (trimming).
●      The longest search text that is allowed.
●      What happens if the search text is blank.
●      Matching text inside the title, with no care for upper or lower case.
●      How search and status work together at the same time.

Not Included
●      Paging, for example page 1, page 2.
●      Searching any field other than the title.
●      Any frontend or UI work. This plan is for the backend only.
Current Repository Evidence
●      The GET /todos route from M08. It reads all todos, in one fixed order, oldest first.
●      The status filter from M09/M10. It adds a status query field, checked with Zod, and changes the WHERE clause in the repository.
●      The todos table. It has a title field, which is what the search will look at.
●      db.ts and Drizzle. These build the database query in code, not by joining raw text. This keeps the query safe from bad input.
●      The style used so far: route, service, repository, with Zod for checks and Result types for errors. M12 will use the same style.

Acceptance Criteria
Search matches a case-insensitive title substring.
Supplied blank search and overlong search are rejected.
Status and search combine with AND.
Query values are handled safely by Drizzle.
Filtering, ordering, and empty results remain correct.

Expected Failures
Failure
When it happens
How it is shown
BlankSearchValue
search is sent, but it is empty or only spaces after trimming.
Result.err({ type: "BlankSearchValue" }). Returns 400.
SearchValueTooLong
The trimmed search text is longer than the allowed maximum.
Result.err({ type: "SearchValueTooLong", max: 100 }). Returns 400.

Unexpected Failures
●      Example: the database is down, or the filtered and searched read query fails.
●      These are caught at the repository. They become Result.err({ type: "UnexpectedError", cause }). The error is logged. The client only sees a plain 500 message, with no internal details.
●      No error should ever escape without being caught. The route uses ts-pattern to handle every possible Result, for the query checks and the database read.
Responsibilities
Layer
What it does
Route
Reads the query string. Checks it with Zod: search must be trimmed, not blank if present, and not too long. Works together with the existing status check. Calls the service with the checked values. Turns the Result into an HTTP response.
Service
Takes the checked search text and status. Asks the repository for the matching todos. Passes the Result through.
Repository
Runs one SELECT on the todos table, using Drizzle to safely add a case-insensitive title match and the existing status filter to the WHERE clause. Keeps the same ordering as M08. Catches any database error and turns it into UnexpectedError.

Certainty Checks
What comes into the system?
An optional search query field, and the existing optional status query field, both on GET /todos.
How will it be checked?
A Zod schema checks that search, is present, is trimmed, is not blank, and is not too long. What will the operation return when it succeeds?
200, with a list of todos that match the search text and the status, if given. Same shape as M08.
What expected failures can happen?
BlankSearchValue, SearchValueTooLong, plus the existing InvalidStatusValue, DuplicateStatusParam, and UnknownQueryParam from M09/M10. All return 400.
How will each expected failure be represented?
As a Result.err with a type field, matched exhaustively with ts-pattern at the route, and turned into the response.
Where will the route, business rules, and database work live?
Route: reads and checks the query string, for both search and status. Service: passes the checked values along. Repository: builds the safe database query for both.
What tests will you write before implementation?
They cover matching, trimming, blank input, length limits, combining search with status, safe querying, and regression checks.
