Objective
Add page-number pagination to the filtered and searched list.

Included
● The default page and page size when none are given.
● The smallest and largest page size allowed.
● How the total number of items and total number of pages are counted.
● The order that filtering, searching, counting, and paging happen in.
● What happens when a client asks for a page that does not exist.
● The extra information sent back with the list, such as total items and total pages.

Not Included
● Changing how status filtering works.
● Changing how search works.
● Sorting choices for the client to pick.
● "Load more" or infinite scroll style paging. This milestone only covers page numbers.
● Any frontend or UI work. This plan is for the backend only.
Current Repository Evidence
● The GET /todos route from M08. It reads all todos, in one fixed order, oldest first.
● The status filter from M09/M10. It adds a status query field and changes the WHERE clause in the repository.
● The search filter from M11/M12. It adds a search query field and changes the WHERE clause in the repository, combined with status using AND.
● db.ts and Drizzle. These are used to build safe database queries, including limit and offset for paging.
● The style used so far: route, service, repository, with Zod for checks and Result types for errors. M14 will use the same style.
Acceptance Criteria
page and pageSize use the agreed defaults and limits.
Filtering and search happen before counting and pagination.
totalItems and totalPages are correct.
A page beyond the results returns an empty list.
Stable ordering prevents duplicate or skipped items within the tested data.
All earlier list behaviour remains green.

Expected Failures
Failure
When it happens
How it is shown
InvalidPageValue
page is sent, but it is not a whole number, or it is less than 1.
Result.err({ type: "InvalidPageValue" }). Returns 400.
InvalidPageSizeValue
pageSize is sent, but it is not a whole number, or it is outside 1 to 100.
Result.err({ type: "InvalidPageSizeValue", min: 1, max: 100 }). Returns 400.

Unexpected Failures
● Example: the database is down, or the count query or the page query fails.
● These are caught at the repository. They become Result.err({ type: "UnexpectedError", cause }). The error is logged. The client only sees a plain 500 message, with no internal details.
● No error should ever escape without being caught. The route uses ts-pattern to handle every possible Result, for the query checks and the database read.
Responsibilities
Layer
What it does
Route
Reads the query string. Checks it with Zod: page and pageSize must be valid whole numbers within their limits, working alongside the existing status and search checks. Calls the service. Turns the Result into an HTTP response.
Service
Takes the checked page, pageSize, status, and search. Asks the repository for the matching count and the matching page of todos. Builds the totalPages value. Passes the combined Result through.
Repository
Runs a count query and a select query with limit and offset, using Drizzle, applying the same status and search conditions to both. Keeps the same ordering as M08. Catches any database error and turns it into UnexpectedError.
Hook
Not used. This milestone has no frontend.
View
Not used. This milestone has no frontend.

Certainty Checks
What comes into the system?
Optional page and pageSize query fields, alongside the existing optional status and search fields, all on GET /todos.
How will it be checked?
A Zod schema checks that page and pageSize, if present, are whole numbers within their allowed ranges. The existing status and search checks still apply.
What will the operation return when it succeeds?
200, with an object containing items (the one page of todos), page, pageSize, totalItems, and totalPages.
What expected failures can happen?
InvalidPageValue, InvalidPageSizeValue, plus the existing failures from M09/M10 and M11/M12. All return 400.
How will each expected failure be represented?
As a Result.err with a type field, matched exhaustively with ts-pattern at the route, and turned into the response.
Where will the route, business rules, and database work live?
Route: reads and checks the query string, for page, pageSize, status, and search. Service: works out totalPages and shapes the final response. Repository: runs the count query and the limited, offset query.
What tests will you write before implementation?
. They cover defaults, limits, ordering of operations, out-of-range pages, response shape, and regression checks.
How will you prove the whole operation works through its real boundaries?
An integration test will insert a known number of todos with different titles and statuses into a real test database, then call the real route with different page, pageSize, status, and search combinations, and check the exact items and metadata returned.
Does this change multiple records or call another system?
No. This only reads from one table, with extra filters and limits. Nothing is changed, and no other system is involved.
If this is frontend work, what states are needed?
Not applicable. This milestone is backend only.
Tests to Write First
● 1. Route: GET /todos with no page or pageSize uses the default page (1) and default pageSize (20).
● 2. Route: GET /todos?page=2&pageSize=5 returns the correct five todos for page two, based on the fixed order.
● 3. Route: pageSize below 1, or above 100, returns 400 with InvalidPageSizeValue.
● 4. Route: page below 1, or not a whole number, returns 400 with InvalidPageValue.
● 5. Route: totalItems reflects the count after status and search are applied, not the count of all todos in the table.
● 6. Route: totalPages is correctly worked out from totalItems and pageSize, for a few different combinations.
● 7. Route: a page number beyond the last real page returns 200 with an empty items list, and correct totalItems and totalPages.
● 8. Route: GET /todos?status=active&search=milk&page=1&pageSize=5 applies status and search first, then counts, then pages the result.
● 9. Route: the same todo never appears on two different pages, and no todo is skipped, when paging through a known set of results in order.
● 10. Repository: the count query and the page query use the same status and search conditions.

Expected First Failure
The page and pageSize query fields are not read yet, and the response is still a plain list, not an object with items and metadata. So test 1 will fail because the response shape does not match what is expected. This shows pagination is genuinely missing before implementation starts.
