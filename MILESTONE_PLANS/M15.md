Objective
Plan how to get one todo by ID.

Included
● How the todoId in the URL is checked.
● The exact shape of a successful reply.
● What happens when no todo has that ID.
● How the repository looks up one todo.
● The exact list of errors this endpoint can return, and no others.
● The tests to write before the code.
Not Included
● Editing or deleting a todo — those already exist as PATCH and DELETE.
● Listing many todos — that is GET /todos, already built.
● Any change to status filtering, search, or pagination.
● Any frontend or UI work. This plan is for the backend only.
Current Repository Evidence

● todo.repository.ts already has an update(id, patch) function that returns TODO_NOT_FOUND when no row matches. A new findById(id) function will follow the same not-found pattern.
● todo.errors.ts already defines TodoErrors.notFound(id) and maps it to 404 in toHttpError. GET /todos/:todoId will reuse this, not invent a new error type.
● todo.contracts.ts already has TodoIdParamSchema and TodoSchema. TodoSchema is what a single todo looks like, and this endpoint returns exactly one, so no new response schema is needed.
Acceptance Criteria
Invalid UUIDs return validation errors.
Existing todos return the exact success contract.
Missing todos return 404 todo_not_found.
No broader error type is exposed than the operation can produce.
Real API integration tests pass.

Expected Failures
Failure
When it happens
How it is shown
VALIDATION_ERROR
The todoId in the path is not a valid UUID.
TodoIdParamSchema.safeParse fails. Returns 400.
NOT_FOUND (todo_not_found)
The todoId is a valid UUID, but no todo with that ID exists.
Result.err(TodoErrors.notFound(id)). Returns 404.

Unexpected Failures
● Example: the database is down, or the lookup query fails for a reason other than "no row found."
● These are caught at the repository. They become Result.err({ type: "UnexpectedError", cause }), the same pattern already used by every other endpoint. The error is logged. The client only sees a plain 503 message, with no internal details.
● No error should ever escape without being caught. The route uses ts-pattern to handle every possible Result: the valid case, the not-found case, and the unexpected-error case, and nothing else.
Responsibilities
Layer
What it does
Route
Checks the todoId in the path with TodoIdParamSchema, the same schema already used by PATCH and DELETE. Calls the service. Turns the Result into an HTTP response: 200, 400, 404, or 503, and nothing else.
Service
Takes the checked todoId. Asks the repository to find it. Passes the Result straight through, since there is no extra business rule needed for a plain lookup.
Repository
Runs one SELECT on the todos table by id, using db.ts. Returns TODO_NOT_FOUND when no row matches, the same pattern already used by update(id, patch). Catches any database error and turns it into UnexpectedError.
Hook
Not used. This milestone has no frontend.
View
Not used. This milestone has no frontend.

Certainty Checks
What comes into the system?
A todoId in the URL path, on GET /todos/:todoId. Nothing else.
How will it be checked?
TodoIdParamSchema checks the todoId is a valid UUID, exactly the same schema already used by PATCH /todos/:id and DELETE /todos/:id.
What will the operation return when it succeeds?
200, with the one matching todo, in the same shape TodoSchema already defines.
What expected failures can happen?
An invalid UUID (400), or a valid UUID with no matching todo (404, todo_not_found).
How will each expected failure be represented?
As a Result.err with a type field, matched exhaustively with ts-pattern at the route, and turned into the response — the same pattern already used across every other endpoint in this file.
Where will the route, business rules, and database work live?
Route: checks the todoId format and shapes the response. Service: passes the checked ID to the repository, no extra logic needed. Repository: runs the lookup and reports not-found or unexpected error.
What tests will you write before implementation?
Listed below, in order. They cover the invalid-ID case, the not-found case, the success case, and one real end-to-end test.
How will you prove the whole operation works through its real boundaries?
An integration test will create a real todo in a real test database, fetch it by its real ID through the real route, then request a random ID that was never created and confirm it returns 404.
Does this change multiple records or call another system?
No. This only reads one row from one table. Nothing is changed, and no other system is involved.
If this is frontend work, what states are needed?
Not applicable. This milestone is backend only.
Tests to Write First
● 1. Route: GET /todos/not-a-uuid returns 400 with VALIDATION_ERROR.
● 2. Route: GET /todos/<a well-formed but unused UUID> returns 404 with a todo_not_found error.
● 3. Route: GET /todos/<an existing todo's ID> returns 200 with the exact todo shape.
● 4. Route: a database error from the service surfaces as 503, not as a raw error or a 404.
● 5. Service: findById passes a valid ID straight to the repository and returns whatever Result the repository gives back.
● 6. Repository: findById returns the matching row when one exists.
● 7. Repository: findById returns TODO_NOT_FOUND when no row matches the given ID.
● 8. Repository: a simulated database failure is wrapped as UnexpectedError, not thrown.
● 9. Integration: a real todo is created through POST /todos, then fetched by its real ID through GET /todos/:todoId and matches exactly; a second request with a random unused UUID returns 404.
Expected First Failure
The route GET /todos/:todoId does not exist yet, so test 1 (and every other route test) will fail with 404 Not Found from Fastify's own router, not from the app's own todo_not_found error. This shows the route is genuinely missing before implementation starts.
