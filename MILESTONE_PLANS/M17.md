Objective
Plan full replacement of a todo's mutable fields.

Included
● Why both title and completed are required on this endpoint, unlike PATCH.
● Why PUT does not create a todo when the ID does not exist.
● How the request body is checked.
● When updatedAt changes, and what the client can and cannot set directly.
● How the saved todo is checked before it is sent back.
● The exact list of errors this endpoint can return.
● The tests to write before the code.
Not Included
● Partial updates — that is PATCH /todos/:id, already built.
● Creating a new todo — that is POST /todos, already built.
● Any change to status filtering, search, or pagination.
● Any frontend or UI work. This plan is for the backend only.
Current Repository Evidence
● todo.route.ts already has PATCH /todos/:id, which accepts title and completed as both optional, since PATCH is a partial update. PUT /todos/:todoId is a different contract: both fields become required, since PUT means "this is now the whole resource," not "change only what I sent."
● todo.contracts.ts already has UpdateTodoRequestSchema, used by PATCH, with title and completed both optional. PUT needs its own schema, since making both fields required is a different contract, not a stricter version of the same one.
● todo.repository.ts already has an update(id, patch) function that returns TODO_NOT_FOUND when no row matches. PUT will reuse this same repository function and the same not-found behaviour, since the underlying SQL UPDATE is the same shape either way.
● todo.errors.ts already defines TodoErrors.notFound(id) and TodoErrors.emptyTitle(), both reused by PUT.
● todo.contracts.ts already has TodoSchema, which is what a full todo looks like. PUT returns exactly this shape, the same as POST and PATCH.
Acceptance Criteria
Both mutable fields are required.
Missing and unknown fields are rejected.
IDs and timestamps cannot be supplied or changed by the client.
A missing todo returns 404 and is not created.
The updated todo is returned and validated.
Repository, service, route, and integration tests pass.

Contracts
Input
PUT /todos/00000000-0000-0000-0000-000000000001
Content-Type: application/json

{
"title": "string",
"completed": false
}
Both title and completed are required. No other field is accepted — id, createdAt, and updatedAt are never read from the body, even if the client sends them.
Success
200 OK
{
"id": "uuid",
"title": "string",
"completed": false,
"createdAt": "ISO-8601 timestamp"
}
Success means the todo at the given ID now has exactly the title and completed value the client sent. id and createdAt never change. updatedAt (once added to the schema) changes to the time of this request.
Update Timing
The update happens in a single database UPDATE statement, the same pattern already used by PATCH. There is no separate read-then-write step, so there is no window where a concurrent request could read a half-updated todo. The repository's update(id, patch) function already does this correctly and PUT reuses it unchanged.
Expected Failures
Failure
When it happens
How it is shown
VALIDATION_ERROR
The todoId in the path is not a valid UUID.
TodoIdParamSchema.safeParse fails. Returns 400.
VALIDATION_ERROR
title or completed is missing, title is blank, or an unknown field is present.
ReplaceTodoRequestSchema.safeParse fails. Returns 400.
NOT_FOUND (todo_not_found)
The todoId is a valid UUID, but no todo with that ID exists.
Result.err(TodoErrors.notFound(id)). Returns 404. No todo is created.

These are the only expected failures for this endpoint. No other failure type is exposed.
Unexpected Failures
● Example: the database is down, or the update query fails for a reason other than "no row found."
● These are caught at the repository. They become Result.err({ type: "UnexpectedError", cause }), the same pattern already used by every other endpoint. The error is logged. The client only sees a plain 503 message, with no internal details.
● No error should ever escape without being caught. The route uses ts-pattern to handle every possible Result: the valid case, the not-found case, and the unexpected-error case, and nothing else.
Responsibilities
Layer
What it does
Route
Checks the todoId with TodoIdParamSchema. Checks the body with a new, strict ReplaceTodoRequestSchema requiring both title and completed, rejecting unknown fields. Calls the service. Turns the Result into an HTTP response: 200, 400, 404, or 503.
Service
Takes the checked todoId, title, and completed. Calls the repository's existing update(id, patch) function with both fields set. Passes the Result straight through.
Repository
Reuses the existing update(id, patch) function unchanged — the same single UPDATE statement, the same TODO_NOT_FOUND behaviour already used by PATCH. No new repository function is needed.
Hook
Not used. This milestone has no frontend.
View
Not used. This milestone has no frontend.

Certainty Checks
What comes into the system?
A todoId in the URL path, and a body with title and completed, both required, on PUT /todos/:todoId.
How will it be checked?
TodoIdParamSchema checks the path, the same schema already used by GET, PATCH, and DELETE. A new ReplaceTodoRequestSchema checks the body: title and completed both required, no other fields accepted.
What will the operation return when it succeeds?
200, with the full, updated todo, in the same shape TodoSchema already defines.
What expected failures can happen?
An invalid UUID, a missing or invalid body field, an unknown body field, or a valid UUID with no matching todo (404, todo_not_found, and no todo is created).
How will each expected failure be represented?
As a Result.err with a type field, matched exhaustively with ts-pattern at the route, the same pattern already used across every other endpoint in this file.
Where will the route, business rules, and database work live?
Route: checks the todoId and the full replacement body. Service: passes the checked values to the repository, no extra logic needed. Repository: reuses the existing update(id, patch) function unchanged.
What tests will you write before implementation?
Listed below, in order. They cover missing fields, unknown fields, the not-found case, the success case, and one real end-to-end test.
How will you prove the whole operation works through its real boundaries?
An integration test will create a real todo through POST /todos, replace it through the real PUT route, confirm the response and a fresh GET both show the new values, then attempt a PUT on a random unused UUID and confirm it returns 404 and creates nothing.
Does this change multiple records or call another system?
No. This changes exactly one row in one table. Nothing else is involved.
If this is frontend work, what states are needed?
Not applicable. This milestone is backend only.
Tests to Write First
● 1. Route: PUT /todos/not-a-uuid returns 400 with VALIDATION_ERROR, before any lookup happens.
● 2. Route: a body missing title returns 400 with VALIDATION_ERROR.
● 3. Route: a body missing completed returns 400 with VALIDATION_ERROR.
● 4. Route: a body with an extra, unknown field (for example id or updatedAt) returns 400 with VALIDATION_ERROR.
● 5. Route: a body with a blank title returns 400 with VALIDATION_ERROR.
● 6. Route: PUT on a well-formed but unused UUID returns 404 with a todo_not_found error, and no new row is created.
● 7. Route: PUT on an existing todo's ID with a valid body returns 200 with the exact updated todo shape.
● 8. Route: a database error from the service surfaces as 503, not as a raw error.
● 9. Service: the replace function passes the checked todoId, title, and completed straight to the repository's update function.
● 10. Repository: update(id, patch) with both fields set replaces the row and returns it — reusing existing repository test coverage, no new repository function needed.
● 11. Regression: every existing PATCH, DELETE, and GET /todos/:todoId test still passes unchanged.
● 12. Integration: a real todo is created, replaced through PUT, confirmed via a fresh GET, then a PUT on a random unused UUID is confirmed to return 404 with nothing created.
Expected First Failure
The route PUT /todos/:todoId does not exist yet, so test 1 (and every other route test) will fail with Fastify's own router 404, not the app's own validation or todo_not_found errors. This shows the route is genuinely missing before implementation starts.
