Current Repository Evidence
● todo.route.ts already has a PATCH /todos/:id handler. It was built earlier, before PUT existed, and currently accepts title and completed as both optional but does not reject an empty object {} or unknown fields. This milestone hardens that existing route rather than building PATCH from scratch.
● todo.contracts.ts already has UpdateTodoRequestSchema, with title and completed both optional. This is the schema the existing PATCH route uses. It needs a refinement added so an empty object is rejected, since two independently optional fields do not forbid both being absent at once.
● todo.repository.ts already has an update(id, patch) function that returns TODO_NOT_FOUND when no row matches. The existing PATCH route already reuses this repository function, the same way M17's PUT plan does.
● todo.errors.ts already defines TodoErrors.notFound(id) and TodoErrors.emptyTitle(), both already used by the existing PATCH route.
● M17's plan for PUT /todos/:todoId already established that PUT requires both title and completed, rejects unknown fields, and never creates a missing todo. Now that PUT is built, PATCH must be hardened so its contract is visibly different from PUT's, not a looser copy of it.
One thing to check later: confirm the exact route path, PATCH /todos/:todoId, matches the :id param name already used elsewhere, the same open question raised in M15 and M17.

Contracts
Input
PATCH /todos/00000000-0000-0000-0000-000000000001
Content-Type: application/json

{ "title": "string" }

or

{ "completed": true }

or

{ "title": "string", "completed": true }
At least one of title or completed must be present. Sending neither is rejected. Sending any field other than title or completed is rejected.
Success
200 OK
{
"id": "uuid",
"title": "string",
"completed": false,
"createdAt": "ISO-8601 timestamp"
}
Success means the todo at the given ID now reflects only the fields the client sent. Any field the client did not send keeps its previous value exactly. id and createdAt never change.
Empty-Object Rejection
A request body of {} is rejected with a validation error before it ever reaches the repository. This is different from PUT, which always requires both fields; PATCH requires at least one field, but zero fields is always invalid, regardless of which endpoint is being used.
Title Validation
If title is present in the request, it must be a non-empty string after trimming, the same rule already used by POST and by the existing UpdateTodoRequestSchema. If title is not present at all, no title validation applies, and the existing title is left untouched.
Missing-Todo Behaviour
If no todo exists with the given ID, PATCH returns 404, the same as GET /todos/:todoId, PUT /todos/:todoId, and DELETE /todos/:id already do. PATCH never creates a new todo, for the same reason given in M17: the server always assigns IDs at creation time, through POST.
Expected Failures
Failure
When it happens
How it is shown
VALIDATION_ERROR
The todoId in the path is not a valid UUID.
TodoIdParamSchema.safeParse fails. Returns 400.
VALIDATION_ERROR
The body is an empty object, has an unknown field, or title is present but blank.
UpdateTodoRequestSchema.safeParse fails, or a refined check rejects the empty object. Returns 400.
NOT_FOUND (todo_not_found)
The todoId is a valid UUID, but no todo with that ID exists.
Result.err(TodoErrors.notFound(id)). Returns 404. No todo is created.

These are the only expected failures for this endpoint.
Unexpected Failures
● Example: the database is down, or the update query fails for a reason other than "no row found."
● These are caught at the repository. They become Result.err({ type: "UnexpectedError", cause }), the same pattern already used by every other endpoint. The error is logged. The client only sees a plain 503 message, with no internal details.
● No error should ever escape without being caught. The route uses ts-pattern to handle every possible Result: the valid case, the not-found case, and the unexpected-error case, and nothing else.
Responsibilities
Layer
What it does
Route
Checks the todoId with TodoIdParamSchema. Checks the body with UpdateTodoRequestSchema, rejecting an empty object and unknown fields. Calls the service. Turns the Result into an HTTP response: 200, 400, 404, or 503.
Service
Takes the checked todoId and whichever fields were sent. Calls the repository's existing update(id, patch) function with only those fields. Passes the Result straight through.
Repository
Reuses the existing update(id, patch) function unchanged — the same single UPDATE statement, only setting the columns present in patch, the same TODO_NOT_FOUND behaviour already used by PUT.
Hook
Not used. This milestone has no frontend.
View
Not used. This milestone has no frontend.

Certainty Checks
What comes into the system?
A todoId in the URL path, and a body with title, completed, both, or neither, on PATCH /todos/:todoId.
How will it be checked?
TodoIdParamSchema checks the path, the same schema already used by GET, PUT, and DELETE. UpdateTodoRequestSchema checks the body: at least one of title or completed must be present, title must be non-empty if sent, and no unknown fields are accepted.
What will the operation return when it succeeds?
200, with the full, updated todo, showing the changed fields and every unchanged field exactly as it was.
What expected failures can happen?
An invalid UUID, an empty body, an unknown body field, a blank title, or a valid UUID with no matching todo (404, todo_not_found, nothing created).
How will each expected failure be represented?
As a Result.err with a type field, matched exhaustively with ts-pattern at the route, the same pattern already used across every other endpoint in this file.
Where will the route, business rules, and database work live?
Route: checks the todoId and the partial body, including the empty-object rejection. Service: passes only the sent fields to the repository. Repository: reuses the existing update(id, patch) function unchanged.
What tests will you write before implementation?
Listed below, in order. They cover each accepted shape, the empty-object and unknown-field rejections, the not-found case, and a direct PATCH-versus-PUT comparison.
How will you prove the whole operation works through its real boundaries?
An integration test will create a real todo, PATCH only its title and confirm completed is unchanged, PATCH only its completed value and confirm title is unchanged, then attempt a PATCH on a random unused UUID and confirm 404 with nothing created.
Does this change multiple records or call another system?
No. This changes exactly one row in one table. Nothing else is involved.
If this is frontend work, what states are needed?
Not applicable. This milestone is backend only.

● 12. Repository: update(id, patch) with only one field set changes only that column, reusing existing repository coverage — no new repository function needed.

● 14. Integration: a real todo is created, patched with title only, confirmed via a fresh GET that completed is unchanged, then patched with completed only, confirmed that title is unchanged, then a PATCH on a random unused UUID is confirmed to return 404 with nothing created.
Expected First Failure
The existing PATCH route currently accepts an empty object {} and unknown fields without rejecting them, since UpdateTodoRequestSchema has no refinement against that yet. So test 1 will fail by showing today's lenient behaviour succeed (200) where the hardened contract requires a 400. This proves the gap is real before the hardening work starts, rather than proving the route is missing — the route already exists.
