Objective
Plan deletion of one todo.

Included
● How the todoId in the URL is checked.
● What a successful delete returns.
● What happens when no todo has that ID.
● What happens if the same delete is sent more than once.
● What the repository and the service are each responsible for.
● The tests to write, including tests that confirm the todo is really gone.
Not Included
● Deleting more than one todo at a time, or deleting by status (that is a separate existing endpoint, DELETE /todos/completed).
● Creating, reading, or editing a todo — those are POST, GET, PUT, and PATCH, already built.
● Any change to status filtering, search, or pagination.
● Any frontend or UI work. This plan is for the backend only.
Current Repository Evidence
● todo.repository.ts already has a delete(id) function, used by the existing DELETE /todos/:id route in earlier files seen in this project. If it already returns void without checking whether a row actually existed, that is the main gap this plan needs to close, since the acceptance evidence requires a real 404 on a missing todo, not a silent success.
● todo.errors.ts already defines TodoErrors.notFound(id), reused here the same way GET, PUT, and PATCH already do.
● todo.contracts.ts already has TodoIdParamSchema, reused here unchanged.
● End-to-end coverage for this milestone is provided two ways: the existing vitest-based e2e file (used since M09–M20) was extended with a new DELETE describe block, and a new Playwright suite was added alongside it, hitting the real running API over HTTP. Both cover DELETE, neither replaces the other.
Acceptance Criteria
Existing todos are deleted and return 204 with no body.
Missing todos return 404 todo_not_found.
A repeated delete leaves the expected final database state.
Integration tests verify the resource is no longer returned.

Contracts
Input
DELETE /todos/00000000-0000-0000-0000-000000000001
The only input is the todoId in the URL path. There is no request body and no query string for this endpoint.
Success
204 No Content
Success means the todo at the given ID has been removed from the database. The response has no body, the same convention already used by DELETE /todos/completed and POST /todos/toggle-all.
Expected Failures
Failure
When it happens
How it is shown
VALIDATION_ERROR
The todoId in the path is not a valid UUID.
TodoIdParamSchema.safeParse fails. Returns 400.
NOT_FOUND (todo_not_found)
The todoId is a valid UUID, but no todo with that ID exists.
Result.err(TodoErrors.notFound(id)). Returns 404.

These are the only expected failures for this endpoint.
Unexpected Failures
● Example: the database is down, or the delete query fails for a reason other than "no row found."
● These are caught at the repository. They become Result.err({ type: "UnexpectedError", cause }), the same pattern already used by every other endpoint. The error is logged. The client only sees a plain 503 message, with no internal details.
● No error should ever escape without being caught. The route uses ts-pattern to handle every possible Result: the valid case, the not-found case, and the unexpected-error case, and nothing else.
Responsibilities
Layer
What it does
Route
Checks the todoId with TodoIdParamSchema. Calls the service. Turns the Result into an HTTP response: 204, 400, 404, or 503. Owns no business logic.
Service
Takes the checked todoId. Calls the repository's delete function. Passes the Result straight through.
Repository
Runs one DELETE on the todos table by id, using db.ts. Must report whether a row was actually deleted, not just that the query ran, so the route can tell an existing delete apart from a missing one. Catches any database error and turns it into UnexpectedError.
Hook
Not applicable. This milestone has no frontend.
View
Not applicable. This milestone has no frontend.

Certainty Checks
What comes into the system?
A todoId in the URL path, on DELETE /todos/:todoId.
How will it be checked?
TodoIdParamSchema checks the todoId is a valid UUID, the same schema already used by GET, PUT, and PATCH.
What will the operation return when it succeeds?
204, with no response body.
What expected failures can happen?
An invalid UUID (400), or a valid UUID with no matching todo (404, todo_not_found).
How will each expected failure be represented?
As a Result.err with a type field, matched exhaustively with ts-pattern at the route, the same pattern already used across every other endpoint in this file.
Where will the route, business rules, and database work live?
Route: checks the todoId format and shapes the response. Service: passes the checked ID to the repository, no extra logic needed. Repository: runs the delete and reports whether a row actually existed.
What tests will you write before implementation?
Listed below, in order. They cover the current-behaviour baseline, the invalid-ID case, the not-found case, the success case, the repeated-delete case, and two real end-to-end tests — one in the existing vitest e2e file, one in a new Playwright suite.
How will you prove the whole operation works through its real boundaries?
Two real end-to-end tests: the existing vitest e2e file creates a real todo, deletes it through the real route, confirms 204, then GETs the same ID and confirms 404. Separately, a new Playwright suite creates a real todo over HTTP, deletes it, confirms 204, then lists todos and confirms it no longer appears. Both confirm a second delete on the same ID returns 404, not a second 204.
Does this change multiple records or call another system?
Not applicable
If this is frontend work, what states are needed?
Not applicable. This milestone is backend only.
Tests to Write First
● 1. Route: confirm the current behaviour of the existing DELETE /todos/:id handler on a missing ID, before any change — this is the baseline the plan checks against, the same discipline used for PATCH in M19/M20.
● 2. Route: DELETE on an existing todo's ID returns 204 with no response body.
● 3. Route: DELETE on a well-formed but unused UUID returns 404 with a todo_not_found error.
● 4. Route: DELETE with an invalid UUID in the path returns 400 with VALIDATION_ERROR, before any lookup happens.
● 5. Route: a database error from the service surfaces as 503, not as a raw error or a 404.
● 6. Route: sending the same DELETE twice on the same ID returns 204 then 404, never 204 twice.
● 7. Service: the delete function passes the checked todoId straight to the repository and returns whatever Result the repository gives back.
● 8. Repository: delete(id) reports success when a matching row existed and was removed.
● 9. Repository: delete(id) reports TODO_NOT_FOUND when no row matched, rather than reporting a false success.
● 10. Repository: a simulated database failure is wrapped as UnexpectedError, not thrown.
● 11. Regression: every existing GET, POST, PUT, and PATCH test still passes unchanged.
● 12. Vitest end-to-end: a real todo is created, deleted through the real route, confirmed gone via a fresh GET returning 404, and a second delete on the same ID is confirmed to return 404, not 204.
● 13. Playwright end-to-end: a real todo is created over HTTP, deleted through the real route, confirmed gone via a fresh list of todos, and a second delete on the same ID is confirmed to return 404. A malformed id is confirmed to return 400.
Expected First Failure
The existing DELETE /todos/:id handler was already present before this plan, since it had been built in an earlier milestone alongside PATCH. Test 1 showed its real gap directly: delete(id) always reported success, so a delete on a missing todo returned 204 instead of the required 404. This is the exact behaviour test 9 and the repository fix in step 3 below close.
