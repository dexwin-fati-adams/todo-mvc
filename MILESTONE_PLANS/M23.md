Objective
Plan an atomic operation that marks the complete collection active or complete.

Included
● The exact request shape: only a completed field is accepted.
● Why this operation applies to every todo in the table, not a filtered subset or one page.
● Why the update must be atomic — all rows change together, or none do.
● What the response reports, including the count of todos affected.
● What happens when the collection is empty.
● The tests to write, including a transaction test and a real API integration test.
Not Included
● Filtering which todos get updated — this operation always targets the whole collection, unlike GET /todos which supports status and search.
● Creating, reading, replacing, or deleting a single todo — those are POST, GET, PUT, PATCH /todos/:id, and DELETE, already built.
● Deleting all completed todos — that is the separate, existing DELETE /todos/completed endpoint.
● Any frontend or UI work. This plan is for the backend only.
Current Repository Evidence
● todo.repository.ts already has an updateAllCompleted(completed: boolean) function, used internally by toggleAll(). This function currently returns ResultAsync<void, TodoDbError> — it does not report how many rows were affected, which this milestone's acceptance evidence explicitly requires ("the returned count is correct, including an empty collection").
● Before starting M24, confirm directly whether a PATCH /todos handler already exists on main, the same way PATCH /todos/:id and DELETE /todos/:id both turned out to already exist before their own milestones: git show main:apps/api/src/modules/todos/todo.route.ts | grep -A 5 'fastify.patch("/todos"'.
Acceptance Criteria
The request accepts only completed.
The operation affects every todo, not only one filter or page.
The update is atomic.
The returned count is correct, including an empty collection.
Transaction and API integration tests pass.

Contracts
Input
PATCH /todos
Content-Type: application/json

{ "completed": true }

or

{ "completed": false }
completed is required and must be a boolean. No other field is accepted, including title, id, or anything else.
Success
200 OK
{
"updatedCount": 5
}
Success means every todo in the table now has the completed value the client sent. updatedCount reports exactly how many rows were changed by the operation.
Expected Failures
Failure
When it happens
How it is shown
VALIDATION_ERROR
completed is missing, is not a boolean, or the body contains an unknown field.
SetAllCompletedRequestSchema.safeParse fails. Returns 400.

Unexpected Failures
● Example: the database is down, or the update transaction fails partway through and rolls back.
● These are caught at the repository. They become Result.err({ type: "UnexpectedError", cause }), the same pattern already used by every other endpoint. The error is logged. The client only sees a plain 503 message, with no internal details.
● If the transaction rolls back, no todo is left partially updated — the database returns to exactly the state it was in before the request, since the whole operation runs as one statement inside one transaction.
Responsibilities
Layer
What it does
Route
Checks the body with a new, strict schema requiring exactly completed as a boolean. Calls the service. Turns the Result into an HTTP response: 200 with the count, 400, or 503.
Service
Takes the checked completed value. Calls the repository's update-all function. Passes the returned count straight through into the response shape.
Repository
Runs one UPDATE todos SET completed = $1 statement inside a transaction, using db.ts. Reports back how many rows were affected, using Drizzle's row count or .returning(). Catches any database error and turns it into UnexpectedError.
Hook
Not used. This milestone has no frontend.
View
Not used. This milestone has no frontend.

Certainty Checks
What comes into the system?
A body with exactly one field, completed, a required boolean, on PATCH /todos.
How will it be checked?
A new, strict Zod schema requiring completed as a boolean, rejecting a missing value, a non-boolean value, and any other field, including title.
What will the operation return when it succeeds?
200, with { "updatedCount": N }, where N is the exact number of todos changed, including 0 for an empty collection.
What expected failures can happen?
Only a validation failure — a missing or invalid completed field, or an unknown field. There is no not-found case for this endpoint.
How will each expected failure be represented?
As a Result.err with a type field, matched exhaustively with ts-pattern at the route, the same pattern already used across every other endpoint in this file.
Where will the route, business rules, and database work live?
Route: checks the request body. Service: passes the checked value to the repository and shapes the count into the response. Repository: runs the single atomic UPDATE and reports the affected row count.
What tests will you write before implementation?
Listed below, in order. They cover the baseline check, validation, the full-collection scope, the count in the response, the empty-collection case, atomicity, and one real end-to-end test.
How will you prove the whole operation works through its real boundaries?
An integration test seeds a real test database with a mix of completed and active todos, calls the real route, and confirms every single row now matches the requested value and the reported count matches exactly how many rows existed.
Does this change multiple records or call another system?
Yes — this is the one operation in this project explicitly designed to change every row in the table at once. It runs as a single transaction so the change is all-or-nothing, with no other system involved.
If this is frontend work, what states are needed?
Not applicable. This milestone is backend only.
Tests to Write First
● 1. Route: confirm whether a PATCH /todos handler already exists and record its current behaviour, before any change — the same discipline used before PATCH /todos/:id and DELETE /todos/:id.
● 2. Route: a body missing completed returns 400 with VALIDATION_ERROR.
● 3. Route: a body where completed is not a boolean (for example a string) returns 400 with VALIDATION_ERROR.
● 4. Route: a body with an extra, unknown field (for example title) returns 400 with VALIDATION_ERROR.
● 5. Route: PATCH /todos with { completed: true } on a mix of active and completed todos returns 200, and every todo is now completed.
● 6. Route: PATCH /todos with { completed: false } on a mix of active and completed todos returns 200, and every todo is now active.
● 7. Route: the response body's updatedCount exactly matches the number of todos that existed before the call.
● 8. Route: calling this on an empty collection returns 200 with { updatedCount: 0 }, not an error.
● 9. Route: a database error from the service surfaces as 503, not as a raw error.
● 10. Repository: the update runs as a single statement inside a transaction, not as a loop of per-row updates — verified by asserting the transaction/query call count.
● 11. Repository: the reported count matches the number of rows actually changed.
● 12. Repository: a simulated database failure is wrapped as UnexpectedError, not thrown, and no partial update is left behind.
● 13. Regression: every existing GET, POST, PUT, PATCH /todos/:id, DELETE, and toggle-all test still passes unchanged.
● 14. Integration: a real test database is seeded with a known mix of active and completed todos, PATCH /todos is called with each completed value, and every row plus the reported count is confirmed through the real route.
Expected First Failure
If no PATCH /todos handler exists yet, every route test will fail with Fastify's own router 404, showing the route is genuinely missing. If a similar handler already exists under a different contract (for example, if toggle-all's behaviour was ever exposed under this path), test 1 will show that real, current behaviour directly, so the gap between what exists and what this milestone requires is confirmed before any code changes, not assumed.

Risks and Assumptions
● Assumes this new PATCH /todos operation is intentionally separate from the existing POST /todos/toggle-all, since toggle-all auto-decides direction and this operation requires an explicit client-supplied value. This should be confirmed with the team rather than assumed, since the two could be seen as overlapping.
● Assumes updateAllCompleted's current return type (void, no count) is the main gap to close, based on the existing toggleAll implementation, and should be confirmed once the real file is checked against main.
● Assumes Drizzle's update().returning() or an equivalent row-count mechanism is available and reliable for reporting the affected count without a separate SELECT.
● Assumes no login is needed for this endpoint, since this whole project has no auth yet.
