Objective
Plan an atomic operation that removes every completed todo.

Included
● The one required selector: status=completed, on the collection route DELETE /todos.
● Why every other collection DELETE request — missing status, a different value, a duplicate, or an unknown query key — is rejected, not defaulted or silently accepted.
● Why the deletion must run as one atomic transaction.
● What the response reports, including the count of todos deleted, and the empty-result case.
● The tests to write, including a transaction test and a real API integration test.
Not Included
● Deleting active todos, or deleting by any selector other than status=completed.
● Deleting one todo by id — that is the existing DELETE /todos/:id, already built.
● Setting every todo's completed value — that is the separate PATCH /todos operation planned in M23/M24.
● Any frontend or UI work. This plan is for the backend only.
Current Repository Evidence
● todo.route.ts already has a DELETE /todos/completed handler (a path segment, not a query parameter), and todo.service.ts already has clearCompleted(), backed by todo.repository.ts's deleteAllCompleted(). That existing endpoint takes no query at all, deletes every completed todo, and returns 204 with no body — it does not report a count.
. ● Before starting M26, confirm directly whether a DELETE /todos handler that reads a status query already exists on main: git show main:apps/api/src/modules/todos/todo.route.ts | grep -B2 -A 10 'fastify.delete("/todos"'.
● deleteAllCompleted() currently returns ResultAsync<void, TodoDbError> — it does not report how many rows were deleted, which this milestone's acceptance evidence explicitly requires ("the delete is atomic and returns the correct count"). Closing that gap, the same way updateAllCompleted needed a count added for M23/M24, is likely the main repository change needed.
● StatusQuerySchema already exists in todo.contracts.ts for GET /todos, accepting status as one of all, active, or completed, defaulting to all when omitted. That schema is the wrong shape for this endpoint: GET /todos treats a missing status as "no filter," but this DELETE endpoint must treat a missing status as a rejected request, since there is no safe default for a collection delete.
Acceptance Criteria
Only status=completed is accepted on the collection DELETE route.
Missing, different, duplicate, and unknown query parameters are rejected.
Every completed todo is deleted, regardless of page or search state.
Active todos remain.
The delete is atomic and returns the correct count.

Contracts
Input
DELETE /todos?status=completed
status is required and must be exactly the single value completed. No other value, no duplicate status key, and no other query key of any kind is accepted.
Success
200 OK
{
"deletedCount": 3
}
Success means every todo that was completed at the moment the request ran has been removed from the database. deletedCount reports exactly how many rows were removed.
Expected Failures
Failure
When it happens
How it is shown
VALIDATION_ERROR
status is missing, is any value other than completed, is sent more than once, or the query contains any other key.
A new, strict Zod schema fails. Returns 400.

Unexpected Failures
● Example: the database is down, or the delete transaction fails partway through and rolls back.
● These are caught at the repository. They become Result.err({ type: "UnexpectedError", cause }), the same pattern already used by every other endpoint. The error is logged. The client only sees a plain 503 message, with no internal details.
● If the transaction rolls back, no todo is left partially deleted — the database returns to exactly the state it was in before the request.
Responsibilities
Layer
What it does
Route
Checks the query string with a new, strict schema requiring exactly status=completed and nothing else. Calls the service. Turns the Result into an HTTP response: 200 with the count, or 400, or 503.
Service
Calls the repository's delete-all-completed function. Passes the returned count straight through into the response shape.
Repository
Runs one DELETE FROM todos WHERE completed = true statement inside a transaction, using db.ts. Reports back how many rows were removed, using Drizzle's .returning() or row count. Catches any database error and turns it into UnexpectedError.
Hook
Not used. This milestone has no frontend.
View
Not used. This milestone has no frontend.

Certainty Checks
What comes into the system?
A query string on DELETE /todos, which must contain exactly one key, status, with exactly one value, completed.
How will it be checked?
A new, strict Zod schema requiring status to be the literal value completed, rejecting a missing value, any other value, a duplicate key, and any unknown key — distinct from the existing StatusQuerySchema used by GET /todos, which allows all, active, or completed and defaults when omitted.
What will the operation return when it succeeds?
200, with { "deletedCount": N }, where N is the exact number of completed todos removed, including 0 when none were completed.
What expected failures can happen?
Only a validation failure — a missing, wrong, duplicated, or accompanied-by-unknown-keys status value. There is no not-found case for this endpoint.
How will each expected failure be represented?
As a Result.err with a type field, matched exhaustively with ts-pattern at the route, the same pattern already used across every other endpoint in this file.
Where will the route, business rules, and database work live?
Route: checks the query string. Service: calls the repository and shapes the count into the response. Repository: runs the single atomic DELETE and reports the affected row count.
What tests will you write before implementation?
Listed below, in order. They cover the baseline check, every rejected-request case, the full-collection scope, the count in the response, the empty-result case, atomicity, and one real end-to-end test.
How will you prove the whole operation works through its real boundaries?
An integration test seeds a real test database with a mix of completed and active todos, calls the real route, and confirms every completed todo is gone, every active todo remains, and the reported count matches exactly how many completed todos existed.
Does this change multiple records or call another system?
Yes — like PATCH /todos, this is one of the few operations in this project explicitly designed to change many rows in the table at once. It runs as a single transaction so the change is all-or-nothing, with no other system involved.
If this is frontend work, what states are needed?
Not applicable. This milestone is backend only.
