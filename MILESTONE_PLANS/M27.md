Objective
Plan the web application shell and read-only todo list.

Included
• The app shell: page layout, header, and main landmark.
• A read-only todo list that loads from GET /todos.
• A contract for the list response and the error response, validated with Zod.
• An API adapter. It is the only place that calls fetch.
• A query hook that owns the server state.
• Application-owned server states: initial loading, initial failure, empty list, ready, refreshing, refresh failure.
• A flow component that maps hook state to the right view.
• A view component that only renders props.
• Accessibility for every state.
• Reference styling, matched to the approved reference design.
• Component, flow, adapter, and browser tests.
Not included
• Creating, editing, completing, or deleting todos. Those are later milestones.
• Filters, search, or pagination controls. The list uses the default GET /todos request.
• Any backend change. The API is already built.
• Authentication. The project has no auth yet.
• Optimistic updates or mutations of any kind.

Contracts
Input
• The user opens the page. There is no form input.
• The adapter sends GET /todos with no query.
• The hook may refetch on demand (a refresh action) or on window focus.
Success
• The adapter returns a validated list of todos.
• Each todo has at least an id, a title, and a completed value (confirm the exact fields from `todo.contracts.ts`).
• The view shows each todo as a list item. Completed todos look different from active ones and are also marked in text, not only by colour.
Expected failures
Failure
When it happens
How it is represented
NETWORK_ERROR
fetch throws, or the request times out
Adapter returns Result.err({ type: "NetworkError" })
HTTP_ERROR
The API returns a non-2xx status such as 503
Adapter returns Result.err({ type: "HttpError", status })
INVALID_RESPONSE
The response body fails the Zod schema
Adapter returns Result.err({ type: "InvalidResponse" })
VALIDATION_ERROR
The API returns 400 with an error body
Adapter validates the error body and returns it as a typed error

The flow matches these types exhaustively with ts-pattern. This is the same pattern the API already uses.
Unexpected failures
• Example: a bug throws inside the adapter, or the error body has an unknown shape.
• The adapter catches it and returns a generic UnexpectedError. It never throws to the hook.
• The view shows a plain message. It never shows raw errors, stack traces, or internal details.
• The error is logged to the console in development only.

Certainty checks
What information enters the system?
The GET /todos response body and status code. There is no user input in this milestone.
How will you check that information?
The adapter validates the success body and the error body with Zod. Invalid data becomes InvalidResponse. The rest of the app only sees validated types.
What will the operation return when it succeeds?
A validated list of todos. The hook turns it into empty or ready.
What expected failures can happen?
Network failure, non-2xx status, invalid response body, and a 400 error body from the API.
How will each expected failure be represented?
As a Result.err with a type field in the adapter. The flow matches every type exhaustively with ts-pattern. The view gets a state, not an error object.
Where will the route, business rules, and database or UI work live?
Page: layout only. Flow: state mapping. Hook: server state. Adapter: fetch and validation. View: rendering. There is no database work.
What tests will you write before implementation?
Listed below. They cover the adapter, the hook, the flow, the view, all six states, accessibility, and one real browser test.
How will you prove the whole operation works through its real boundaries?
A Playwright test starts the app against a real test API and database. It seeds todos, opens the page, and checks the list. It also checks the empty state, the failure state, and a refresh that keeps the list.
Does this change multiple records or call another system? If yes, how will failure be handled safely?
It calls the API, but it only reads. No records change. Failures become typed errors and safe messages, as described above.
If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?
• Loading: role="status" message, announced politely.
• Empty: a clear text message, not a blank area.
• Ready: a semantic list (ul and li). Completed state is shown in text and style.
• Error: role="alert" message with a Retry button that is keyboard reachable.
• Refreshing: aria-busy="true" on the list region. The list stays visible.
• Refresh failure: role="alert" message. The list stays visible.
• Pending: not applicable. There are no mutations in this milestone.
• Page: one h1, a main landmark, visible focus rings, and sufficient colour contrast.
