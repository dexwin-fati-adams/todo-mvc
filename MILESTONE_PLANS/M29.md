Objective
Plan the frontend path for creating one todo.

Included
•      A create-todo form above the list: one text field and one submit button.
•      Title validation before any request, using the shared CreateTodoRequestSchema.
•      A pending state that blocks repeated submission.
•      Success: the list refreshes, the field is cleared, and focus returns to the field.
•      Expected failure: an empty title, on the client and as a 400 from the API.
•      Unexpected failure: network error, 503, or an invalid response.
•      An adapter method, a mutation hook, a flow, and a view for the form.
•      Focus behaviour and accessibility for every state.
•      User-facing messages for every state.
•      Adapter, hook, flow, form, and browser tests.
Not included
•      Editing, completing, or deleting todos.
•      Filters, search, or pagination controls.
•      Any backend change. POST /todos is already built.
•      Optimistic updates. The list changes only after the API succeeds.
•      A title length limit. The shared contract has none.
•      Authentication. The project has no auth yet.

Contracts
Input
•      The user types a title in the text field and presses the button or the Enter key.
•      The flow trims the title, then checks it with CreateTodoRequestSchema.
•      The adapter sends POST /todos with the body { "title": "<trimmed title>" }.
Success
•      The API returns 201 with a todo that passes TodoSchema.
•      The list query is invalidated and refetched. The list shows the new todo.
•      The title field is empty.
•      Focus is in the title field, ready for the next todo.
•      The pending message is gone and no error is shown.
Expected failures
Failure When it happens How it is represented
EMPTY_TITLE The trimmed title is empty. No request is made. The flow shows the validation message under the field. The field has aria-invalid="true" and takes focus.
SERVER_VALIDATION The API returns 400 VALIDATION_ERROR. The adapter returns API_ERROR with status 400. The flow shows the same validation message. The raw server message is not shown.
 
Unexpected failures
•      Network error, 503, an unreadable body, or any status that is not 201 or 400.
•      The adapter returns a typed error: NETWORK_ERROR, API_ERROR, or PARSE_ERROR. It never throws.
•      The form shows one safe message with role="alert". It never shows raw errors, status codes, or internal details.
•      The typed title stays in the field, so the user can try again.
•      The error is cleared when the user types again or submits again.

Responsibilities
Layer Responsibility Contract
Contract Reuse CreateTodoRequestSchema, TodoSchema, and ErrorResponseSchema from the shared package. No new schema. Imported from contracts
Route or page App.tsx mounts the form flow above the list flow. No logic. Renders <TodoCreateFlow />
Service or flow TodoCreateFlow owns the form state: idle, invalid, pending, failed. It trims and validates the title, blocks repeated submits, calls the hook, clears the field on success, and moves focus. Title in, view props out
Repository or API adapter todoApi.create(body) in todo.api.ts. It sends POST /todos, validates the 201 body with TodoSchema, and returns a Result. It is still the only code that calls fetch. create(body): ResultAsync<Todo, ClientError>
Hook useCreateTodo wraps todoApi.create in a TanStack Query mutation. On success it invalidates the ["todos"] queries. It exposes submit, isPending, and error. { submit, isPending, error, reset }
View TodoFormView renders props only: field, button, validation message, pending message, error alert. It has no fetch and no hooks. Props: title, status, message, inputRef, onChange, onSubmit
 
Certainty checks
What information enters the system?
The title text from the form field. The API response to POST /todos.
How will you check that information?
The flow trims the title and checks it with CreateTodoRequestSchema before any request. The adapter checks the 201 body with TodoSchema and the error body with ErrorResponseSchema.
What will the operation return when it succeeds?
A validated todo. The flow clears the field, refreshes the list, and restores focus.
What expected failures can happen?
An empty title on the client, and a 400 VALIDATION_ERROR from the API.
How will each expected failure be represented?
The client check is a validation state in the flow. The server 400 is API_ERROR with status 400 from the adapter. Both show the same message. Matching uses ts-pattern with .exhaustive().
Where will the route, business rules, and database or UI work live?
Page: layout. Flow: validation, pending guard, focus. Hook: mutation and list refresh. Adapter: fetch and response checks. View: rendering. There is no database work.
What tests will you write before implementation?
Listed below: adapter, hook, flow, form view, shell, and browser tests.
How will you prove the whole operation works through its real boundaries?
A Playwright test opens the page against the real API and test database, types a title, submits, and checks that the new todo is in the list, the field is empty, and focus is in the field. It also checks that an empty submit sends no request.
Does this change multiple records or call another system? If yes, how will failure be handled safely?
It creates one record through the API. A failure leaves the list unchanged, shows a safe message, and keeps the typed title. No partial state is possible.
If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?
•      Idle: an empty field and an enabled button.
•      Invalid: a message under the field, aria-invalid, focus on the field.
•      Pending: the button is disabled and reads "Adding…". A role="status" message says "Adding todo…".
•      Success: the field is empty, focus is in the field, and the list shows the new todo.
•      Failure: a role="alert" message. The title stays.
•      Accessibility: a visible label linked to the field, a real form and a submit button, the Enter key works, visible focus ring, and no information by colour alone.

Risks and assumptions
•      The shared contract does not trim, so the client must trim. The API would accept a whitespace-only title. Fixing the API is outside this milestone, so I will report it.
•      There is no title length limit in the contract. The form will not invent one.
•      The new todo may not appear on page 1 if the API sorts it later. The list uses the default page, so I will check the order in the browser test.
•      A double submit is blocked in the browser by the pending guard. The API itself has no duplicate check, so two quick requests would create two todos if the guard failed.
•      Invalidating ["todos"] shows the existing refreshing state, which keeps the current todos on screen.
•      Assumes no login is needed, because the project has no auth yet.
