Objective
Plan how one todo row becomes complete or active through PATCH /todos/:id.
Included
•	A checkbox on every todo row.
•	A request that sends only { "completed": true } or { "completed": false }.
•	A pending state for the row that is being changed.
•	Blocking repeated changes on a row while its request is pending.
•	Failure recovery: no false completed state is ever shown.
•	Stale data: the todo was deleted or already changed elsewhere.
•	Refreshing the list after the change.
•	Checkbox labels and focus behaviour.
•	An adapter method, a mutation hook, flow changes, and view changes.
•	Adapter, hook, flow, component, and browser tests.
Not included
•	Editing a todo title.
•	Toggling every todo at once.
•	Deleting a todo.
•	Filters, search, pagination controls, or routing.
•	Optimistic updates. The checkbox never changes before the API answers.
•	Any backend change. PATCH /todos/:id is already built.
•	Authentication. The project has no auth yet.

Contracts
Input
•	The user clicks a row checkbox, or presses Space on it.
•	The flow works out the wanted value from the todo the row shows: completed: !todo.completed.
•	The wanted value is sent as an absolute value, never as a toggle. Two quick clicks cannot flip the todo twice.
•	The adapter sends PATCH /todos/:id with the body { "completed": <boolean> } and the id encoded in the path.
•	The body is checked with UpdateTodoRequestSchema before the request leaves the adapter flow.
Success
•	The API returns 200 with a todo that passes TodoSchema.
•	The ["todos"] queries are invalidated and refetched. The list shows the new state from the server.
•	The row text is struck through when the todo is complete.
•	The pending message is gone, and no error is shown.
•	Focus stays on the checkbox.
Expected failures
Failure	When it happens	How it is represented
NOT_FOUND	The API returns 404. The todo was deleted somewhere else.	The adapter returns API_ERROR with status 404. The row shows the stale-data message and the list is refreshed, so the row disappears.
VALIDATION_ERROR	The API returns 400. The request was not valid.	The adapter returns API_ERROR with status 400. The row shows the generic message and keeps its old state.

Unexpected failures
•	Network error, 503, an unreadable body, or any other status.
•	The adapter returns a typed error: NETWORK_ERROR, API_ERROR, or PARSE_ERROR. It never throws.
•	The row shows one safe message with role="alert". It never shows raw errors, status codes, or server messages.
•	The checkbox returns to the state the server last confirmed. The list is not refreshed, so what the user sees is the last known truth.
•	The message is cleared when the user tries again.
Stale data
•	The checkbox always shows todo.completed from the list data. It is a controlled input. No local state decides what it shows.
•	A click does not change what it shows. Only new data from the server does. This is why a failure can never leave a false completed state.
•	Absolute values make the request safe to repeat. If another browser already changed the todo to the same value, the request succeeds and nothing changes.
•	If the todo was changed to the opposite value elsewhere, the request still wins. The API has no version check, so the last write wins. I will report this as a risk.
•	If the todo was deleted elsewhere, the 404 triggers a refresh, and the stale row is removed.

Certainty checks
What information enters the system?
A click or Space key on a row checkbox, and the API response to PATCH /todos/:id.
How will you check that information?
The flow works out the wanted value from the row data. The body is checked with UpdateTodoRequestSchema. The adapter checks the 200 body with TodoSchema and the error body with ErrorResponseSchema.
What will the operation return when it succeeds?
The updated todo. The flow refreshes the list and shows the new state from the server.
What expected failures can happen?
A 404 when the todo no longer exists, and a 400 when the request is not valid.
How will each expected failure be represented?
As API_ERROR with a status, from the adapter. The flow matches it with ts-pattern and .exhaustive() and chooses a message.
Where will the route, business rules, and database or UI work live?
Flow: the wanted value, the pending guard, and the messages. Hook: the mutation and the list refresh. Adapter: fetch and response checks. View: rendering. There is no database work.
What tests will you write before implementation?
Listed below: adapter, hook, flow, component, page, and browser tests. Every one starts from a placeholder, so it fails on a missing behaviour and not on a broken import.
How will you prove the whole operation works through its real boundaries?
A Playwright test opens the page against the real API and test database, clicks a checkbox, and checks that the row is complete, the list shows it after a refresh, and the API returns completed: true. It also checks a failure with a 503, and a double click.
Does this change multiple records or call another system? If yes, how will failure be handled safely?
It changes one record through the API. A failure leaves the row as it was, shows a safe message, and changes nothing else. No partial state is possible.
If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?
•	Idle: an unchecked or checked box and the title.
•	Pending: the box has aria-disabled, and the row shows "Updating…" with role="status".
•	Success: the new state from the server, with the pending message gone.
•	Failure: a role="alert" message in the row. The box shows the old state.
•	Stale: the 404 message, then the row is removed after the refresh.
•	Accessibility: a real label and checkbox, the Space key works, a visible focus ring, and focus stays on the checkbox after every outcome.
