Objective
Plan how a user edits a todo title and saves it through PUT.


Included
•	Entry into edit mode by double-click, and by an Edit button that a keyboard user can reach.
•	The initial value of the field, and where focus and the cursor go on entry.
•	Title validation before any request.
•	Keeping the completed value when the title is saved.
•	Save, cancel, and the pending state.
•	Repeated-save prevention.
•	Expected and unexpected failures, with recoverable input.
•	Focus behaviour after save, cancel, and failure.
•	Keyboard behaviour: Tab order, Enter, Escape, Space.
•	An adapter method, a mutation hook, a flow, and view changes.
•	Adapter, hook, flow, component, and browser tests.
Not included
•	Editing the completed value. That is M32.
•	Deleting a todo.
•	Toggling every todo at once.
•	Filters, search, pagination controls, or routing.
•	Optimistic updates. The list shows the new title only after the API confirms it.
•	Editing several rows at the same time.
•	A title length limit. The shared contract has none.
•	Any backend change. PUT /todos/:id is already built.
•	Authentication. The project has no auth yet.

Contracts
Input
•	Entry: a double-click on the title, or Enter or Space on the row's Edit button.
•	Edit: the user types in the field. The flow keeps the draft text.
•	Save: Enter in the field, or the Save button.
•	Cancel: Escape in the field, or the Cancel button.
•	On save the flow trims the draft and checks it with ReplaceTodoRequestSchema.
•	The body is { "title": "<trimmed title>", "completed": <the todo's current completed value> }.
•	The adapter sends PUT /todos/:id with that body and the id encoded in the path.
Success
•	The API returns 200 with a todo that passes TodoSchema.
•	The ["todos"] queries are invalidated and refetched. The list shows the new title from the server.
•	Edit mode closes.
•	Focus returns to the row's Edit button.
•	The pending message is gone, and no error is shown.
Expected failures
Failure	When it happens	How it is represented
EMPTY_TITLE	The trimmed title is empty. No request is made.	The flow shows the validation message under the field. The field has aria-invalid="true" and takes focus.
SERVER_VALIDATION	The API returns 400.	The adapter returns API_ERROR with status 400. The flow shows the same validation message and keeps the draft.
NOT_FOUND	The API returns 404. The todo was deleted somewhere else.	The adapter returns API_ERROR with status 404. The editor stays open with the stale-data message and the draft. The list is refreshed when the user cancels.
UNCHANGED	The trimmed title equals the current title.	No request is made. Edit mode closes as if the user had cancelled.

Unexpected failures
•	Network error, 503, an unreadable body, or any other status.
•	The adapter returns a typed error: NETWORK_ERROR, API_ERROR, or PARSE_ERROR. It never throws.
•	The editor shows one safe message with role="alert". It never shows raw errors, status codes, or server messages.
•	The editor stays open, and the draft stays in the field, so the user can try again.
•	The message is cleared when the user types again or saves again.
Responsibilities
Layer	Responsibility	Contract
Contract	Reuse ReplaceTodoRequestSchema, TodoSchema, and ErrorResponseSchema from the shared package. No new schema.	Imported from contracts
Route or page	App.tsx is unchanged. The editor lives inside the list row.	None
Service or flow	A flow hook, useTodoEditFlow, owns the edit state: which row is open, the draft, the status, and the message. It trims and checks the draft, reads completed from the row, blocks a repeated save with a ref, calls the hook, and moves focus. TodoFlows uses it and passes the result to the view.	None
Repository or API adapter	todoApi.replace(id, body) in todo.api.ts. It sends PUT /todos/:id, checks the 200 body with TodoSchema, and returns a Result. It stays the only code that calls fetch.	None
Hook	useReplaceTodo wraps todoApi.replace in a mutation. After a success it invalidates the ["todos"] queries. It does not refresh after a 404, because that would remove the row and the draft. It exposes refresh() for the flow to call on cancel. It never throws.	{ replace, refresh }
View	TodoItem shows either the title with the Edit button, or TodoEditForm. TodoEditForm renders props only: the field, Save, Cancel, the pending message, and the error.	Props: draft, status, message, inputRef, onChange, onSave, onCancel

Certainty checks
What information enters the system?
A double-click, an Edit button press, typed text, and the keys Enter and Escape. The API response to PUT /todos/:id.
How will you check that information?
The flow trims the draft and checks { title, completed } with ReplaceTodoRequestSchema before any request. The adapter checks the 200 body with TodoSchema and the error body with ErrorResponseSchema.
What will the operation return when it succeeds?
The updated todo. The flow closes the editor, refreshes the list, and restores focus.
What expected failures can happen?
An empty title, a server 400, a 404 when the todo was deleted, and an unchanged title.
How will each expected failure be represented?
The client checks are states in the flow. The server failures are API_ERROR with a status from the adapter. The flow matches them with ts-pattern and .exhaustive() and chooses a message.
Where will the route, business rules, and database or UI work live?
Flow: validation, the completed value, the pending guard, and focus. Hook: the mutation and the list refresh. Adapter: fetch and response checks. View: rendering. There is no database work.
What tests will you write before implementation?
Listed below: adapter, hook, flow, component, page, and browser tests. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.
How will you prove the whole operation works through its real boundaries?
A Playwright test opens the page against the real API and test database, edits a title, saves, and checks the list and the API. Another edits a completed todo and checks that completed is still true. Others test the keyboard, a validation failure, and a 503.
Does this change multiple records or call another system? If yes, how will failure be handled safely?
It changes one record through the API. A failure leaves the saved todo as it was, keeps the draft, and shows a safe message. No partial state is possible.
If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?
•	Idle: the title and the Edit button.
•	Editing: a labelled field with the current title, Save, and Cancel.
•	Invalid: a message under the field, aria-invalid, focus on the field.
•	Pending: the field is read-only, Save reads "Saving…" and has aria-disabled, and a role="status" message says "Saving…".
•	Failure: a role="alert" message. The draft stays.
•	Stale: the 404 message. The draft stays until the user cancels.
•	Accessibility: real buttons and a real field, a visible focus ring, the keys work, and focus is never lost.
