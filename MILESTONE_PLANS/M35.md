## Objective

Plan how the frontend deletes one todo.

## Included

- A Delete button on every row, with a label that names the todo.
- The adapter method that calls `DELETE /todos/:id`.
- A mutation hook that refreshes the list after the server confirms.
- Pending state on the row, and repeated-click prevention.
- Success: the todo leaves the list only after the server confirms and the list is refreshed.
- A missing todo (404): the todo is already gone, so the list is refreshed and the user is told.
- Unexpected failures (network error, 503, unreadable body, any other status): a safe message the user can act on, and the row stays usable.
- Focus behaviour after success, after a missing todo, and after failure.
- Keyboard behaviour: Tab order, Enter, Space.
- How Delete, Edit (M34), and the checkbox (M32) block each other on one row.
- An adapter method, a mutation hook, a flow, and view changes.
- Adapter, hook, flow, component, and browser tests.

## Not included

- A confirmation dialog or an undo. The requirement does not ask for one. (See Risks.)
- Deleting several todos at once, or "clear completed".
- Optimistic removal. The list drops the todo only after the API confirms.
- Any backend change. `DELETE /todos/:id` is already built.
- Filters, search, pagination controls, or routing.
- Authentication. The project has no auth yet.
- Changing how edit (M34) or toggle (M32) work, beyond blocking them while a delete is pending.

## Contracts

### Input

- Delete: a click, or Enter or Space, on the row's Delete button. The accessible name is `Delete “<title>”`.
- The adapter sends `DELETE /todos/:id` with no body, and the id encoded in the path.

### Success

- The API confirms (expected: `204`, no body).
- The `["todos"]` queries are invalidated and refetched. The hook waits for the refetch, so the row stays in its pending state until the list no longer has the todo.
- The row disappears from the list.
- A polite status message announces `Deleted “<title>”.` so a screen reader user knows what happened.
- Focus moves to the Delete button of the next row. If the deleted row was the last one, focus moves to the previous row's Delete button. If no rows are left, focus moves to the empty message.
- No error is shown.

### Expected failures

| Failure   | When it happens                                                                                  | How it is represented                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NOT_FOUND | The API returns 404. The todo was already deleted somewhere else.                                | The adapter returns `API_ERROR` with status 404. The hook still refreshes the list. The row disappears, and a list notice says `That todo was already deleted. The list has been refreshed.` Focus moves as it does after success. |
| BLOCKED   | The row's toggle is pending, the row is already being deleted, or any row is open in the editor. | No request is made and no message is shown. The Delete button has `aria-disabled="true"`.                                                                                                                                          |

### Unexpected failures

- Network error, 503, 400, an unreadable body, or any other status.
- The adapter returns a typed error: `NETWORK_ERROR`, `API_ERROR`, or `PARSE_ERROR`. It never throws.
- A 400 cannot come from the UI, because the id comes from the server, so it is treated as unexpected.
- The row stays in the list. It shows one safe message with `role="alert"`: `Could not delete this todo. Please try again.` It never shows raw errors, status codes, or server messages.
- The Delete button is usable again, so the user can try again. The message is cleared when the user tries again.
- Focus stays on the Delete button.

## Certainty checks

**What information enters the system?**
A click or key press on Delete, and the API response to `DELETE /todos/:id`.

**How will you check that information?**
The id comes from a todo the list already validated with `TodoSchema`. The adapter checks the status, and reads an error body with `ErrorResponseSchema`.

**What will the operation return when it succeeds?**
A `Result` with no value. The flow refreshes the list, announces the deletion, and moves focus.

**What expected failures can happen?**
The todo was already deleted (404), or the row is busy with a toggle, an edit, or another delete.

**How will each expected failure be represented?**
A 404 is `API_ERROR` with a status from the adapter. A busy row is a state in the flow. The flow matches errors with ts-pattern and `.exhaustive()` and chooses a message.

**Where will the route, business rules, and database or UI work live?**
Flow: the pending guard, the neighbour row, the notice, and focus. Hook: the mutation and the list refresh. Adapter: fetch and response checks. View: rendering. There is no database work.

**What tests will you write before implementation?**
Listed below: adapter, hook, component, flow, boundary, regression, and browser tests. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.

**How will you prove the whole operation works through its real boundaries?**
A Playwright test opens the page against the real API and test database, deletes a todo, and checks the list and the API. Others test the keyboard, a repeated click, a todo deleted elsewhere, a 503, and the empty list.

**Does this change multiple records or call another system? If yes, how will failure be handled safely?**
It deletes one record through the API. A failure leaves the todo in the list, shows a safe message, and lets the user try again. A todo deleted by someone else is handled as a 404. If the delete succeeds but the list refresh fails, the existing refresh-failure banner with Retry shows, and a second delete of the same row gets a 404, which is handled.

**If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?**

- Idle: the title, the Edit button, and the Delete button.
- Pending: the Delete button keeps its label, reads "Deleting…", and has `aria-disabled`. A `role="status"` message says "Deleting…". The checkbox and Edit are blocked.
- Failure: a `role="alert"` message on the row. The row stays and Delete works again.
- Missing todo: a `role="status"` list notice. The row disappears.
- Empty: the empty message takes focus after the last todo is deleted.
- Accessibility: a real button, a name that includes the title, a visible focus ring, the keys work, and focus is never lost.

## Risks and assumptions

- **No confirmation step.** Deleting is permanent and has no undo. The requirement does not ask for a confirmation, so I will not add one. If the reviewer wants one, it becomes a small follow-up milestone.
- **No-body response.** I assume `DELETE` returns `204` with no body. If `send()` or `request()` always parse JSON, they must be fixed first. If the route returns the deleted todo instead, I will check it with `TodoSchema`.
- **Refresh after success.** The hook waits for the list refetch so the row stays pending until it is gone. If the refetch fails, the existing refresh-failure banner shows and the row stays. A second delete gets a 404, which this plan handles.
- **Focus after removal.** The deleted row's button disappears, so focus must be moved on purpose. The flow works out the neighbour before the request. If the neighbour is gone when the list updates, focus falls back to the list.
- **Shared row messages.** Toggle and delete share the row message state in `TodoFlows`. Each action clears the row's message when it starts.
- Ports. The apps use 4000 and 4001.
- Assumes no login is needed, because the project has no auth yet.
