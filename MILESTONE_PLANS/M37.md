## Objective

Plan frontend status filtering.

## Included

- Three controls, All, Active, and Completed, in a labelled group above the list.
- Where the selected filter lives: the URL query string, `?status=active` or `?status=completed`, with no param meaning All.
- Reading the filter from the URL on load, on a click, and on the browser Back and Forward buttons.
- Checking the URL value before it reaches the API. A missing, unknown, or repeated value is treated as All.
- Query keys that give each filter its own result identity.
- Requesting the correct server filter for each control through the existing adapter.
- No stale rows from another filter. While a new filter loads for the first time, the previous filter's rows are not shown.
- Loading, refreshing, empty, and failure states for each filter, and a filter control that stays usable in all of them.
- Selected-filter styling that is visible without relying on colour alone, and is also exposed with `aria-current`.
- Count behaviour: what each control shows, and when it shows nothing.
- An empty message that names the filter, for example `No active todos.`
- Keyboard behaviour: Tab order, Enter, and a visible focus ring.
- A parse helper, a URL hook, a filter component, hook and view changes.
- Parse, URL hook, query hook, component, view, flow, and browser tests.

## Not included

- Search, sorting, pagination controls, or a page size.
- A router library. The filter is read and written with the browser's own URL and History APIs.
- Remembering the filter between visits in local storage or a cookie.
- "Clear completed" or toggle all.
- Moving focus when a toggled row leaves a filtered list. (See Risks.)
- Any backend change. `GET /todos?status=` is already built and tested.
- Optimistic filtering. The list always shows what the server returned for the selected filter.
- Changing how create, toggle, edit (M34), or delete (M36) work, beyond the list refresh they already trigger.

## Contracts

### Input

- A click, or Enter, on the All, Active, or Completed link. Each link has the accessible name `All`, `Active`, or `Completed`, and an `href` of `?status=…` (or the bare path for All).
- Or the URL itself: a page load, or Back and Forward, with `?status=active`, `?status=completed`, or no param.
- The value is read with the shared status schema. Anything that is not exactly one of `active` or `completed` is All.
- The adapter sends `GET /todos?status=<all|active|completed>` and no other param.

### Success

- The API returns the list and its counts for that status.
- The list shows only that response's rows.
- The URL shows the selected filter. Selecting a different filter adds one history entry, so Back returns to the previous filter.
- The selected link has `aria-current="page"` and a visible style. The other links have neither.
- Counts: each control shows its count from the response currently on screen, for example `Active 2`. A control shows no count while its number is unknown (first load of that filter, or a failure). The counts never come from another filter's response.
- When the selected filter has no todos, the empty message names the filter: `No todos yet.` for All, `No active todos.` for Active, and `No completed todos.` for Completed.
- Selecting the filter that is already selected makes no request and adds no history entry.

### Expected failures

| Failure            | When it happens                                       | How it is represented                                                                                                                                          |
| ------------------ | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| INVALID_URL_STATUS | The URL has a missing, unknown, or repeated `status`. | The filter is All. The URL is cleaned with `replaceState`, so the address bar matches the page and Back is not trapped. No request with the bad value is sent. |
| SAME_FILTER        | The user selects the filter that is already selected. | Nothing happens: no request, no history entry, no message.                                                                                                     |

### Unexpected failures

- A network error, 503, 400, or unreadable body on the list request.
- The adapter returns a typed error and never throws. This is the existing M28 and M30 behaviour.
- A first load that fails for a filter shows the existing safe error with Retry for that filter. The filter group stays on screen with the new filter selected, and the user can switch to another filter. Rows from the previous filter are not shown.
- A refresh that fails for a filter that already has rows keeps that filter's own rows and shows the existing refresh-failure banner with Retry.
- Raw errors and status codes are never shown.

## Certainty checks

**What information enters the system?**
A click or key press on a filter link, a URL with a `status` value, and the API response to `GET /todos?status=…`.

**How will you check that information?**
The URL value is parsed with the shared status schema, and only a single exact value is accepted. The adapter reads the response with the existing contract schemas.

**What will the operation return when it succeeds?**
The selected status, and a list and counts that belong to that status only.

**What expected failures can happen?**
The URL has an invalid, missing, or repeated `status`, or the user selects the filter that is already selected.

**How will each expected failure be represented?**
Both are states in the filter hook. An invalid value becomes All and the URL is cleaned. A repeated selection is ignored. The hook matches values with ts-pattern and `.exhaustive()`.

**Where will the route, business rules, and database or UI work live?**
URL: the browser address, read and written only in `useStatusFilter`. Parsing: one helper. Query identity: `useTodos`. Fetch and response checks: the adapter. Rendering: `StatusFilter` and `TodoView`. There is no database work.

**What tests will you write before implementation?**
Listed below: parse, URL hook, query hook, component, view, flow, boundary, regression, and browser tests. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.

**How will you prove the whole operation works through its real boundaries?**
Playwright opens the page against the real API and test database, clicks each control, and checks the requests, the rows, the URL, and the selected state. Other tests reload with a filter in the URL, use Back, load an invalid URL, and slow down a response.

**Does this change multiple records or call another system? If yes, how will failure be handled safely?**
No records change. It only reads the list. A failure shows the existing safe error for the selected filter, and the user can switch filters or retry.

**If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?**

- Loading: the first load of a filter shows the existing loading message and no rows. The filter group is shown with the new filter selected.
- Refreshing: the same filter shows its rows with the existing refreshing status.
- Empty: the message names the filter.
- Ready: the rows of the selected filter, and the counts.
- Error: the existing safe message with Retry, with the filter group still usable.
- Accessibility: links in a labelled `nav`, `aria-current="page"` on the selected one, a selected style that does not depend on colour alone (heavier text and a border), a visible focus ring, and a focus order of All, Active, Completed.

## Risks and assumptions

- **Stale rows.** `useTodos` has no `placeholderData` or `keepPreviousData` today, so a new filter should start with no rows. Nobody must add one later. Tests 14 and 29 and browser test 40 prove it, and they guard against that change.
- **Cached rows of the same filter.** A mutation invalidates every `["todos"]` key. When the user comes back to a filter that was loaded earlier, its own earlier rows show with the refreshing status until the refetch finishes. These rows belong to that filter, so this is allowed, and test 15 shows that rows from another filter never show.
- **Counts.** The API counts all todos for `activeCount` (from `allResult` in the service), so each control can show its number whichever filter is selected, and the All count is `activeCount + completedCount`. If browser test 42 shows that a filtered response has different counts, I will show a count only on the selected control and say so in the plan review.
- **No router.** I assume the app has no router. If it has one, I will use its search-param state and drop `useStatusFilter`'s History code, and the contracts stay the same.
- **Toggled row leaves the list.** In Active or Completed, toggling a todo makes it leave the list after the refetch. The checkbox then disappears, and focus is lost. I will not change this in M38, and I will record it as a follow-up.
- **Create under a filter.** A todo added while Completed is selected does not appear in that list. I will not change this in M38.
- **Empty message and delete.** The delete flow puts focus on the empty message. I will keep it focusable for every filter.
- Ports. The apps use 4000 and 4001.
- Assumes no login is needed, because the project has no auth yet.
