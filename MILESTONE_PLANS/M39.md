## Objective

Plan how a user searches todo titles.

## Included

- One search box above the list, in a labelled search form, with a visible label `Search todos` and a Clear button.
- Where the search lives: the URL query string, `?search=milk`, next to `?status=`. No `search` param means no search.
- Input validation before any request: a blank (spaces only) value and a value that is too long are not sent.
- Request timing: the request is sent 300 ms after the user stops typing, or at once on Enter. Only the last value is requested.
- Query identity: the query key holds the status, the search, and the page, so each combination has its own result.
- Status combination: the search keeps the selected status, and choosing a status keeps the search.
- Page reset: a new search, a cleared search, and a new status all drop the page, so the request is for page 1.
- Clear-search behaviour: Clear (and an emptied box) removes the search and restores the unsearched list for the selected status.
- Loading, refreshing, no results, and failure states for a search, with the box still usable and its text kept.
- An empty message that names the search, for example `No active todos match “milk”.`
- Ignoring late responses: a slow response for an old search never replaces the list for the current search.
- Keyboard and screen-reader behaviour: label, Enter to search, Clear by keyboard, `aria-invalid` and an alert for a bad value, and a visible focus ring.
- A parse helper for the search value and the URL, one shared URL helper, a URL hook, a search box component, and hook and view changes.
- Parse, URL hook, search box, query hook, view, flow, and browser tests.

## Not included

- Pagination controls, a page size control, or sorting. M39 only keeps the page out of a new request, and it reads `page` from the URL for that reason.
- Searching anything except todo titles.
- Highlighting the match in the row.
- Search suggestions, history, or remembering the search in local storage or a cookie.
- Cancelling an in-flight request with an abort signal. Late responses are ignored by the query key instead.
- Input method (IME) composition handling.
- A router library. The URL is read and written with the browser's own URL and History APIs, as in M38.
- Any backend change. `GET /todos?search=` is already built. If the evidence shows otherwise, I will stop and say so.
- Changing how create, toggle, edit, or delete work, beyond the list refresh they already trigger.
- Moving focus when a toggled row leaves a searched list. (See Risks.)

## Contracts

### Input

- Typing in the box named `Search todos`. The value is raw text. It is not trusted.
- Or the URL itself: a page load, or Back and Forward, with `?search=…`, `?status=…`, and `?page=…`.
- A committed search is the trimmed value, from 1 to `SEARCH_MAX_LENGTH` characters. Anything else is not a search.
- The adapter sends `GET /todos?status=<all|active|completed>[&search=<value>][&page=<n>]`. It sends `search` only when a valid search exists, and `page` only when it is greater than 1. `URLSearchParams` does the encoding, so `&`, `#`, `%`, and spaces cannot change the query.

### Success

- The API returns the list for that status and search.
- The list shows only that response's rows.
- The URL shows the committed search and status, and no `page` after a new search. A new committed search uses `replaceState`, so typing does not fill the Back button. Choosing a status still uses `pushState`, as in M38.
- Search and status combine with AND. Choosing Active while searching `milk` shows active todos with `milk` in the title. The Active link keeps `search=milk`.
- Clear (or an emptied box) removes `search` from the URL. The list is the unsearched list for the selected status. The status stays selected.
- No results is a success: the list is empty and the message names the search: `No todos match “milk”.`, `No active todos match “milk”.`, or `No completed todos match “milk”.`
- While a search is active, the status controls show no counts. They come back when the search is cleared.
- Committing the search that is already committed makes no request and no history change.
- The box always shows what the user typed. The list always shows the result of the committed search in the URL.

### Expected failures

| Failure            | When it happens                                                               | How it is represented                                                                                                                                                                                  |
| ------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SEARCH_BLANK       | The box has only spaces, and the user presses Enter or the timer fires.       | No request. The box is marked `aria-invalid`, and the message `Enter a search term, or clear the box to see all todos.` is shown with `role="alert"`. The committed search and the list do not change. |
| SEARCH_TOO_LONG    | The trimmed value is longer than `SEARCH_MAX_LENGTH`.                         | No request. The message `Search can be at most N characters.` is shown. The committed search and the list do not change.                                                                               |
| INVALID_URL_SEARCH | The URL has an empty, blank, too long, or repeated `search`.                  | No search. The URL is cleaned with `replaceState`. No request with the bad value is sent.                                                                                                              |
| INVALID_URL_PAGE   | The URL has a `page` that is not a whole number of 1 or more, or is repeated. | Page 1. The URL is cleaned. No request with the bad value is sent.                                                                                                                                     |
| SAME_SEARCH        | The committed value equals the current search.                                | Nothing happens: no request, no history change, no message.                                                                                                                                            |

An emptied box (`""`) is not a failure. It is Clear.

### Unexpected failures

- A network error, 503, 400, or unreadable body on the list request.
- The adapter returns a typed error and never throws. This is the existing behaviour.
- A first load that fails for a search shows the existing safe error with Retry for that search. The search box and the status controls stay on screen with the user's text kept, and the user can edit, clear, or switch status. Rows from another search are not shown.
- A refresh that fails for a search that already has rows keeps that search's own rows and shows the existing refresh-failure banner with Retry.
- Raw errors, status codes, and server messages are never shown.

## Certainty checks

**What information enters the system?**
Text typed in the search box, a URL with `search`, `status`, and `page` values, and the API response to `GET /todos?...`.

**How will you check that information?**
Typed text is checked by `parseSearch`: trim, then blank, then length. URL values are checked by `parseListParams`: only a single value that passes the same rules is accepted, and a page must be a whole number of 1 or more. The adapter reads the response with the existing contract schemas.

**What will the operation return when it succeeds?**
The committed status, search, and page, and a list that belongs to that combination only.

**What expected failures can happen?**
A blank search, a search that is too long, an invalid URL search or page, and committing the same search again.

**How will each expected failure be represented?**
As values returned by `parseSearch` and `parseListParams`, and as states in `useListParams` and `SearchBox`. No expected failure throws. The code matches them with ts-pattern and `.exhaustive()`.

**Where will the route, business rules, and database or UI work live?**
URL: the browser address, read and written only in `useListParams` through `buildListUrl`. Rules: `parseSearch` and `parseListParams`, from the contract. Query identity: `useTodos`. Fetch and response checks: the adapter. Timing, typed text, and messages: `SearchBox`. Rendering the list: `TodoView`. There is no database work in this milestone.

**What tests will you write before implementation?**
Listed below: parse, URL helper, URL hook, search box, query hook, view, flow, boundary, regression, and browser tests. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.

**How will you prove the whole operation works through its real boundaries?**
Playwright opens the page against the real API and test database, types searches, and checks the requests that were sent, the rows, the URL, and the messages. Other tests combine search with each status, reload with a search in the URL, use Back, hold and release responses out of order, fail a response, and check that bad values never reach the API.

**Does this change multiple records or call another system? If yes, how will failure be handled safely?**
No records change. It only reads the list. A failure shows the existing safe error for the search, keeps the typed text, and the user can edit, clear, retry, or switch status.

**If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?**

- Loading: the first load of a search shows the existing loading message and no rows. The box keeps its text and stays usable.
- Refreshing: the same search shows its rows with the existing refreshing status.
- No results: the message names the search and the status. It is focusable, for the delete flow.
- Ready: the rows of the search, and no counts while a search is active.
- Error: the existing safe message with Retry. The typed text is kept.
- Invalid input: `aria-invalid="true"`, the message linked with `aria-describedby`, and shown with `role="alert"` so a screen reader announces it. Nothing is sent.
- Accessibility: a `form` with `role="search"`, a visible `<label>` for an `input type="search"`, a Clear button with the name `Clear search` (shown only when the box has text), a visible focus ring on both, and a focus order of search box, Clear, All, Active, Completed. After Clear, focus returns to the box. The search text is always rendered as text, never as HTML.

## Risks and assumptions

- **Contract rules.** The search rules (trim, blank, maximum length, title only, case) are assumed until step 1. If the client and the server disagree, the client could send a value the server rejects, so the client takes its rules from the contract and not from a copy.
- **Stale rows and late responses.** `useTodos` has no `placeholderData`, and each query has its own key, so an old response cannot replace the current list. Tests 37, 39, 65, and 66 prove it. Nobody must add `placeholderData` or `keepPreviousData` later.
- **Typing and the Back button.** A debounced search uses `replaceState`, so typing `milk` makes one URL, not four. The cost is that Back does not step through earlier searches. Choosing a status still uses `pushState`.
- **Typed text and the URL can differ.** The box can hold a bad value while the list shows the last good search. The message says why, and the URL is the source of truth for the list. This is deliberate, and test 24 and test 25 show it.
- **Counts.** The counts are hidden while a search is active, because they are assumed to count all todos. Test 70 checks the server. If the server counts follow the search, I can show them, but I will not change that in M39 without telling the manager.
- **Wildcards.** If the server treats `%` or `_` as a wildcard, a search for `%` would match every todo. Test 72 checks this. The fix belongs in the backend, so I would record it and not hide it in the client.
- **Page state.** M39 adds a `page` URL value and key but no page control. If a page control already exists, I will use it for the reset.
- **Changes to M38 code.** `useStatusFilter` is replaced by `useListParams`, `useTodos` takes an object, and the `StatusFilter` links change. The M38 tests move with them. I will keep every M38 behaviour and its tests, and list the moved tests in the pull request.
- **Toggled row leaves the list.** In a searched or filtered list, toggling a todo can make it leave the list after the refetch, and focus is lost. This is the M38 follow-up. I will not change it in M40.
- **Create under a search.** A todo added while a search is active may not match and so will not appear. I will not change this in M40.
- **Empty message and delete.** The delete flow puts focus on the empty message. I keep it focusable for every search, and test 54 checks it.
- **Input method composition.** Text typed with an input method may commit early. Not handled in this milestone.
- Ports. The apps use 4000 and 4001.
- Assumes no login is needed, because the project has no auth yet.
