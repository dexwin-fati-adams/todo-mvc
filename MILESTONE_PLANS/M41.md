## Objective

Plan how the user moves between todo-list pages and changes page size.

## Included

- A pagination bar below the list with a Previous button, a Next button, the text `Page 2 of 5`, and a page-size choice labelled `Todos per page`.
- Where the page state lives: the URL query string, `?page=2&pageSize=10`, next to `?status=` and `?search=`. No `page` means page 1. No `pageSize` means the default size.
- Metadata: the page bar reads `page`, `pageSize`, `totalItems`, and `totalPages` from the list response, and shows `Page X of Y`.
- Previous and Next: each moves one page. Previous is disabled on page 1. Next is disabled on the last page. Both are disabled when there is only one page.
- Page-size choices: 10, 20, 50, and 100, as a native `select`. The default is 20, the same as the server default. Changing the size goes back to page 1.
- Invalid or empty pages: a `page` or `pageSize` that is not valid in the URL is cleaned. A page past the last page comes back empty from the server, and the app recovers to a valid page (see Contracts).
- Query identity: the query key holds the status, the search, the page, and the page size, so each combination has its own result.
- Filter and search interaction: a new status, a new search, and a cleared search all go back to page 1 and keep the page size. Page moves and size changes keep the status and the search.
- Focus and keyboard: visible labels, a visible focus ring, a sensible tab order, and focus that is not lost when a button becomes disabled.
- Loading, refreshing, empty, and failure states for a page, with the page bar still usable.
- Ignoring late responses: a slow response for an old page never replaces the list for the current page.
- A page-size list, a pure `resolvePage` helper for the out-of-range recovery, a hook that remembers the last known page count, a `Pagination` component, and changes to the URL helper, URL hook, query hook, and flow.
- Parse, helper, URL hook, component, query hook, flow, and browser tests.

## Not included

- Numbered page buttons, First and Last buttons, "jump to page", infinite scroll, or "load more".
- Sorting.
- A page-size choice other than 10, 20, 50, and 100, or a free-typed size.
- Remembering the page or the page size in local storage or a cookie. The URL is the only place.
- Cancelling an in-flight request with an abort signal. Late responses are ignored by the query key, as in M38 and M40.
- A router library. The URL is read and written with the browser's own URL and History APIs, as in M38 and M40.
- Any backend change. `GET /todos?page=&pageSize=` is already built. If the evidence shows otherwise, I will stop and say so.
- Showing "Showing 21 to 40 of 53" text. The bar shows only `Page X of Y`.
- Changing how create, toggle, edit, or delete work, beyond the list refresh they already trigger.
- Moving focus when a toggled row leaves a filtered list. (See Risks.)

## Contracts

### Input

- A click or key press on Previous, Next, or the page-size choice.
- Or the URL itself: a page load, or Back and Forward, with `?page=…`, `?pageSize=…`, `?status=…`, and `?search=…`.
- A valid page is a whole number of 1 or more. A valid page size is one of 10, 20, 50, or 100. Anything else is not valid.
- The adapter sends `GET /todos?status=…[&search=…][&page=<n>][&pageSize=<n>]`. It sends `page` only when it is above 1, and `pageSize` only when it is not the default 20. `URLSearchParams` does the encoding.

### Success

- The API returns the rows and the metadata for that status, search, page, and page size.
- The list shows only that response's rows. The bar shows `Page X of Y` from that response.
- Next and Previous use `pushState`, so Back and Forward step through pages. The URL shows `?page=2`, and page 1 removes `page`.
- Changing the page size uses `pushState`, drops the page, and keeps the status and the search. A size equal to the default removes `pageSize` from the URL.
- Choosing a status, committing a search, and clearing a search go to page 1 and keep the page size.
- Previous is disabled on page 1. Next is disabled when the page is the last page. When `totalPages` is 0 or 1, both are disabled and the text is `Page 1 of 1`.
- While the response for a new page is loading, the old rows are hidden, the controls stay on screen, and the bar keeps the last known page count for the same status, search, and page size. So Next stays enabled and focus stays on it while the next page loads. When the status, the search, or the page size changes, the last known count is dropped, and the bar shows `Page X` with Next disabled until the response arrives.
- **Out-of-range recovery (the plan's approved handling).** When the response is empty, the requested page is above 1, and the requested page is past the last page, the app replaces the URL (no new history entry) with the last page. When there are no todos at all (`totalItems` is 0), it replaces the URL with page 1 and shows the normal empty message. The app tells the user with a polite status message: `Page 9 does not exist. Showing page 3.` The recovery runs once, because the target page is always valid. A response that is empty for a page inside the range is shown as it is, so there is no loop.
- Deleting or toggling the last row on a page can make that page empty. The refetch then returns an empty out-of-range page, and the same recovery applies.

### Expected failures

| Failure               | When it happens                                                               | How it is represented                                                                                                           |
| --------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| INVALID_URL_PAGE      | The URL has a `page` that is not a whole number of 1 or more, or is repeated. | Page 1. The URL is cleaned with `replaceState`. No request with the bad value is sent.                                          |
| INVALID_URL_PAGE_SIZE | The URL has a `pageSize` that is not one of the four choices, or is repeated. | The default size. The URL is cleaned. No request with the bad value is sent.                                                    |
| PAGE_OUT_OF_RANGE     | The response is empty, and the page is past the last page.                    | The recovery above: the URL is replaced with a valid page and the status message is shown.                                      |
| NO_MOVE_POSSIBLE      | Previous on page 1, Next on the last page.                                    | The button is disabled, so nothing happens. A call with an invalid page from code is refused: no history change and no request. |
| SAME_PAGE             | The page or size to go to equals the current one.                             | Nothing happens: no request and no history change.                                                                              |

### Unexpected failures

- A network error, 503, 400, or unreadable body on the list request. The adapter returns a typed error and never throws. This is the existing behaviour.
- A first load that fails for a page shows the existing safe error with Retry for that page. The search box, status controls, and page bar stay on screen and usable, so the user can go to another page, change the size, or switch status. Rows from another page are not shown.
- A refresh that fails for a page that already has rows keeps that page's own rows and shows the existing refresh-failure banner with Retry.
- Raw errors, status codes, and server messages are never shown.

## Certainty checks

**What information enters the system?**
Clicks and key presses on the page bar, a URL with `page`, `pageSize`, `status`, and `search` values, and the API response to `GET /todos?...` with its page metadata.

**How will you check that information?**
URL values are checked by `parseListParams`: only a single value that passes the rules is accepted. A page from code is checked in `goToPage`. A page size must be one of the four choices. The adapter reads the response with the existing contract schemas. The response's page metadata is checked by `resolvePage` before the app trusts it for a recovery.

**What will the operation return when it succeeds?**
The chosen status, search, page, and page size in the URL, and a list and page metadata that belong to that combination only.

**What expected failures can happen?**
An invalid page in the URL, an invalid page size in the URL, a page past the end, a move that is not possible, and going to the same page.

**How will each expected failure be represented?**
As values returned by `parseListParams` and `resolvePage`, and as states in `useListParams` and `Pagination`. No expected failure throws. The code matches them with ts-pattern and `.exhaustive()`.

**Where will the route, business rules, and database or UI work live?**
URL: the browser address, read and written only in `useListParams` through `buildListUrl`. Rules: `parseListParams`, `pageSizes`, and `resolvePage`. Query identity: `useTodos`. Fetch and response checks: the adapter. The recovery and the message: `TodoFlows`. The bar: `Pagination`. Rendering the list: `TodoView`. There is no database work in this milestone.

**What tests will you write before implementation?**
Listed below: page-size, parse, page decision, URL helper, URL hook, component, query hook, last-known-count, flow, boundary, regression, and browser tests. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.

**How will you prove the whole operation works through its real boundaries?**
Playwright creates 45 todos through the real API and test database, then clicks Next, Previous, and the page-size choice, and checks the requests that were sent, the rows, the URL, and the page text. Other tests combine paging with each status and with search, reload with the page in the URL, use Back, open a page past the end, delete the last row of the last page, hold and release responses out of order, fail a response, and run the keyboard smoke test.

**Does this change multiple records or call another system? If yes, how will failure be handled safely?**
No records change. It only reads the list. A failure shows the existing safe error for the page, the bar stays usable, and the user can retry, go to another page, change the size, or switch status.

**If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?**

- Loading: the first load of a page shows the existing loading message and no rows. The bar stays on screen with the last known page count, or `Page X` with Next disabled when there is none.
- Refreshing: the same page shows its rows with the existing refreshing status.
- Empty: the existing empty message for the status and search. The bar shows `Page 1 of 1` with both buttons disabled.
- Ready: the rows of the page and `Page X of Y`.
- Error: the existing safe message with Retry. The bar stays usable.
- Recovery: a polite status message (`role="status"`) says which page was shown instead.
- Accessibility: a `nav` named `Pagination`, buttons named `Previous page` and `Next page` that use the real `disabled` attribute, a native `select` with a visible label `Todos per page`, the text `Page X of Y` in a polite live region so a screen reader hears the page change, a visible focus ring on all three controls, and the tab order Previous, Next, size choice, after the search box, status links, and list. When the button that had focus becomes disabled, focus moves to the page text, so the keyboard user is not sent back to the top of the page.

## Risks and assumptions

- **Response shape.** The metadata fields, and the value of `totalPages` for an empty list and for a page past the end, are assumed until step 1. If they differ, `resolvePage` and the page text must change, so I will check them before I write code.
- **Totals and filters.** The plan assumes `totalItems` and `totalPages` follow the status and the search. If they count all todos, the bar would show pages that do not exist for the filtered list. Test 91 checks this. If it is wrong, it is backend work, and I will record it and not hide it in the client.
- **Stale rows and late responses.** `useTodos` has no `placeholderData`, and each key has its own result, so an old response cannot replace the current list. Tests 46 to 49, 84, and 85 prove it. Nobody must add `placeholderData` or `keepPreviousData` later.
- **Recovery and history.** The recovery uses `replaceState`, so Back does not return to the empty page. A user who typed a bad `page` by hand lands on a valid page and is told which one.
- **Recovery loop.** `resolvePage` never returns the page it was given, and a response that is empty inside the range is shown as it is. Tests 13 and 63 prove there is no loop.
- **Focus.** Native `disabled` buttons lose focus, so the bar moves focus to the page text when the focused button becomes disabled. The last known count keeps Next enabled while the next page loads, so focus is not lost on every click. Tests 38, 39, 69, and 87 check this.
- **Last known count can be out of date.** It comes from the same status, search, and page size, but another user may have added or removed todos. The response replaces it as soon as it arrives, and the recovery handles a page that no longer exists.
- **Many todos in browser tests.** The tests need more than 20 todos, so each one creates its todos through the API. This is slower than other tests, so I will create them in one helper and keep the numbers small (21 to 45).
- **Changes to M40 code.** `useListParams`, `useTodos`, and `parseListParams` get new fields, and `TodoFlows` gets a new component and an effect. The M40 tests move with them. I will keep every M40 behaviour and its tests, and list the moved tests in the pull request.
- **Toggled row leaves the list.** In a filtered list, toggling a todo can make it leave the page, and focus is lost. This is the M38 follow-up. M41 only handles the case where the whole page becomes empty (test 66). I will not change the rest in M42.
- **Create under a filter.** A todo added while a filter or search is active may not appear, and a new todo may land on another page. I will not change this in M42.
- **Page size is not remembered.** After a reload without `pageSize` in the URL, the size is 20 again. This is deliberate.
- Ports. The apps use 4000 and 4001.
- Assumes no login is needed, because the project has no auth yet.
