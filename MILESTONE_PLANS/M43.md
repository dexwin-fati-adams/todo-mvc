## Objective

Plan how the standard TodoMVC control changes the complete collection.

## Included

- One "toggle all" checkbox above the list, as in TodoMVC.
- **How the desired boolean is chosen.** The control reads `activeCount` and `completedCount` from the list response. If at least one todo is active, the desired value is `completed: true` ("mark all complete"). If no todo is active and at least one is completed, the desired value is `completed: false` ("mark all active"). If there are no todos at all, the control is not shown. A pure helper, `chooseToggleAll(counts)`, makes this choice. The rows on screen, the page, the status, and the search are never used for the choice.
- **Full-collection wording.** The visible label names the number and the action: `Mark all 45 todos as complete` or `Mark all 45 todos as active`. One line of help text under it says `This changes every todo, including other pages and filters.` The checkbox is described by that help text (`aria-describedby`).
- **Checked state.** The checkbox is checked only when every todo is complete (`activeCount` is 0 and `completedCount` is above 0). A mixed list is unchecked.
- **Pending state.** While the request runs, the checkbox is really `disabled`, a guard also refuses a second call, and a polite status line says `Updating all todos…`. Focus is put back on the checkbox when the request ends, because a disabled control loses focus.
- **Success.** The list and the counts are refreshed (every `["todos"]` key is invalidated). A polite status message says `Marked 45 todos as complete.` or `Marked 45 todos as active.`, using `updatedCount` from the server. The label and the checked state then follow the new counts.
- **Failure.** A safe message in an alert: `Could not update all todos. Please try again.` The list is not changed, the checkbox is enabled again, and the user can try again. No status code or server text is shown.
- **After the refresh.** The M41 recovery still runs: if the user is on `?status=active&page=3` and marks all complete, the page becomes empty, the app moves to a valid page, and the normal empty message shows.
- Tests: pure helper, label, adapter, hook, component, flow, and browser tests.

## Not included

- Any backend change. `PATCH /todos` with `{ "completed": boolean }` is already built and tested. If the evidence shows otherwise, I will stop and say so.
- A confirmation dialog or an undo. (See Risks.)
- Using `POST /todos/toggle-all`. That route flips each todo on its own, so a mixed list stays mixed and just swaps sides. It is not what the control means, so the web does not call it.
- "Clear completed". That is a different milestone.
- Changing only the todos on the current page or in the current filter. The control always means every todo.
- Blocking the single-row checkboxes, Edit, or Delete while the bulk request runs. (See Risks.)
- Optimistic updates. The rows change only after the server answers and the list is refreshed.
- A router library, local storage, or changes to the URL. The control adds nothing to the URL.
- Moving focus when a row leaves a filtered list after the refresh, apart from what M41 already does.

## Contracts

### Input

- A click, or Space on the focused checkbox.
- The counts `{ activeCount, completedCount }` from the list response on screen.
- The adapter sends `PATCH /todos` with the body `{ "completed": <boolean> }` and nothing else. It sends no `status`, `search`, `page`, or `pageSize`.

### Success

- `chooseToggleAll(counts)` returns one of:
  - `{ kind: "none" }` when `activeCount + completedCount` is 0.
  - `{ kind: "set", completed: true }` when `activeCount` is above 0.
  - `{ kind: "set", completed: false }` when `activeCount` is 0 and `completedCount` is above 0.
- The server returns `200` and `{ updatedCount }`. The hook returns `ok({ updatedCount })`.
- The flow refreshes every `["todos"]` key, shows `Marked <updatedCount> todos as complete.` (or `as active.`), and puts focus back on the checkbox if it had focus before.
- If `updatedCount` is 0 (the collection became empty in another tab), the message is `There are no todos to update.` and the list is refreshed.
- The label: `Mark all <total> todos as complete` or `Mark all <total> todos as active`, where `<total>` is `activeCount + completedCount`. For a total of 1 it is `Mark the 1 todo as complete` or `Mark the 1 todo as active`.
- Checked: `activeCount` is 0 and `completedCount` is above 0.
- Visibility and enabled state:

| Situation                                                        | The control                                |
| ---------------------------------------------------------------- | ------------------------------------------ |
| First load, no counts yet                                        | Not shown (no empty box flashes on screen) |
| Counts known, total above 0                                      | Shown, enabled                             |
| Counts known, total is 0                                         | Not shown                                  |
| A new page, status, or search is loading, so no counts on screen | Shown with the last known counts, disabled |
| The request is pending                                           | Shown, really `disabled`                   |
| The list failed to load and there are no counts                  | Not shown                                  |

### Expected failures

| Failure                                     | When it happens                                                 | How it is represented                                                                                                 |
| ------------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| NO_TODOS                                    | The total is 0.                                                 | The control is not shown, so there is nothing to submit. If code calls the flow anyway, it returns without a request. |
| COUNTS_UNKNOWN                              | A new key is loading and the last known counts are not trusted. | The control is disabled, so nothing is submitted.                                                                     |
| ALREADY_PENDING                             | A second click or key press while a request runs.               | The checkbox is `disabled`, and a ref guard also refuses a second call. Only one request is sent.                     |
| API_ERROR (400)                             | The body is refused by the server.                              | The safe failure message. It cannot happen with a valid boolean, and a test pins the body.                            |
| NETWORK_ERROR, API_ERROR (5xx), PARSE_ERROR | The request fails or the response cannot be read.               | The same safe failure message, `Could not update all todos. Please try again.`                                        |

### Unexpected failures

- A thrown error from the adapter is not expected, because it returns a typed `Result`. If something throws anyway, the flow leaves the pending state (in a `finally`) so the control is never stuck disabled, and shows the safe failure message.
- Raw errors, status codes, and server messages are never shown.
- A refresh after success that fails shows the existing refresh-failure banner for the list. The success message still stands, because the update itself worked.

## Certainty checks

**What information enters the system?**
A click or key press on the checkbox, the counts from the list response, and the API response to `PATCH /todos`.

**How will you check that information?**
The counts are numbers that already passed the list response schema. `chooseToggleAll` makes the boolean from them, so it is always a real boolean. The adapter reads the `PATCH` response with `SetAllCompletedResponseSchema` before the app trusts `updatedCount`.

**What will the operation return when it succeeds?**
`ok({ updatedCount })`, then a refreshed list and refreshed counts where every todo has the chosen `completed` value.

**What expected failures can happen?**
No todos, unknown counts, a second submission while pending, a refused body, a network or server error, and an unreadable response.

**How will each expected failure be represented?**
As values: the `none` choice, a disabled control, a `Result` error from the adapter, and a `failed` state in the flow. The code matches them with ts-pattern and `.exhaustive()`. Nothing expected throws.

**Where will the route, business rules, and database or UI work live?**
Route: none. Rules (which boolean, which words): the helper file. Fetch and response checks: the adapter. Refresh after success: the hook. Pending, messages, and focus: the flow. Markup and accessibility: `ToggleAll`. There is no database work in the web.

**What tests will you write before implementation?**
Listed below: helper, label, adapter, hook, component, flow, boundary, regression, and browser tests. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.

**How will you prove the whole operation works through its real boundaries?**
Playwright creates 45 todos through the real API and test database (some complete, some active), goes to page 2 with a filter and a search, clicks the control, and checks the one `PATCH /todos` request body, the request count, and that the rows, the counts, and the other pages all changed. It also holds the response to check the pending state, and fails the request to check the failure state.

**Does this change multiple records or call another system? If yes, how will failure be handled safely?**
Yes. It changes every todo with one `UPDATE` on the server, which is atomic: either every row changes or none. A failure shows the safe message, leaves the list as it was, and lets the user try again.

**If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?**

- Loading: no counts yet, so the control is not shown. While a new page or filter loads, the control shows the last known counts and is disabled.
- Empty: no todos, so the control is not shown.
- Ready: the checkbox, with a label that names the action and the number of todos, and the help text.
- Pending: the checkbox is `disabled`, `aria-busy="true"` is set on the control's wrapper, and the status line says `Updating all todos…`.
- Success: a polite status message (`role="status"`) with the number of todos changed. It stays until the next action, so a screen reader can hear it.
- Error: the safe message in an `alert`. The checkbox is enabled again.
- Accessibility: a real `input type="checkbox"` with a real `label` (`htmlFor`), so the name is the full-collection sentence. `aria-describedby` points to the help text. Space toggles it. A visible focus ring. It sits before the list in the tab order, after the search box and status links. Focus returns to the checkbox after a request, so a keyboard user is not sent back to the top. The checked state is not colour-only: it is the native check mark.

## Risks and assumptions

- **Counts and the search.** The label's number comes from the counts. If they follow the search, the label would be wrong while a search is active. Test 50 checks this, and the plan stops there if it fails.
- **Stale counts.** The desired boolean comes from counts the user saw a moment ago. Another tab may have changed the todos. The result is still correct and safe, because the server sets every todo to the chosen value, and the refresh shows the real state. The message uses the server's `updatedCount`.
- **Mixed state is lost.** Marking all complete and then all active does not bring back the old mix. This is how TodoMVC works. There is no undo and no confirmation in this milestone. If the reviewer wants either, it is a new milestone.
- **Wrong server route.** `POST /todos/toggle-all` exists and looks like a match, but it flips each row. Test 52 pins the route (`PATCH`) and the body.
- **Disabled control loses focus.** A native `disabled` checkbox cannot keep focus. The flow puts focus back when the request ends. Tests 44 and 60 check this.
- **Stuck pending.** If anything throws, the `finally` leaves the pending state. Test 43 checks this.
- **Double submission.** The `disabled` attribute and the ref guard both stop it, because a fast second click can arrive before React re-renders. Tests 38 and 56 check this.
- **Row actions during the request.** A single-row toggle, edit, or delete started during the bulk request can finish before or after it. The final refresh shows the server's real state, so the screen is never wrong for long. I will not block rows in this milestone.
- **Controls and a changing list.** During a page change there are no counts on screen. The control uses the last known counts and is disabled, so it does not flicker away, and nothing can be submitted from unknown counts (test 45).
- **Late refresh.** After the update, a refresh for the current key is requested. Other keys are marked stale and load when they are opened. The list has no `placeholderData`, so an old response cannot replace the current list.
- **Filtered list becomes empty.** Marking all complete under Active empties the list. The M41 recovery handles an empty page past the range, and the normal empty message handles page 1. Test 58 checks this.
- **Changes to M42 code.** `TodoFlows` gets a new component and a new hook. Every test that renders `TodoFlows` needs the new hook mocked. I will list the moved tests in the pull request.
- Ports. The apps use 4000 and 4001.
- Assumes no login is needed, because the project has no auth yet.
