## Objective

Plan how the user deletes all completed todos.

## Included

- One "clear completed" button below the list, as in TodoMVC.
- **Visibility.** The button is on the page only when `completedCount` is above 0. The count comes from the list response and describes all todos, so it does not depend on the page, status, or search. When `completedCount` is 0, the button is not rendered at all, so it cannot be focused or pressed. While there are no counts yet (first load, or a failed first load), it is not shown.
- **Full-collection wording.** The visible button text names the number and the scope: `Clear all 20 completed todos` (and `Clear the 1 completed todo` for one). One line of help text under it says `This deletes every completed todo, including other pages and filters. It cannot be undone.` The button is described by that help text (`aria-describedby`).
- **Pending state.** While the request runs, the button is really `disabled`, a guard also refuses a second call, the wrapper is `aria-busy`, and a polite status line says `Clearing completed todos…`.
- **Success.** The list and the counts are refreshed (every `["todos"]` key is invalidated). A polite status message says `Deleted 20 completed todos.` (or `Deleted 1 completed todo.`), using `deletedCount` from the server. If the server deleted 0, it says `There were no completed todos to delete.` and the list is still refreshed.
- **Failure.** A safe message in an alert: `Could not clear completed todos. Please try again.` The list is not changed, the button is enabled again, and the user can try again. No status code or server text is shown.
- **Focus after deletion.** After a success the button goes away (there are no completed todos left), so focus would be lost. If the button had focus when it was used, focus moves to the status message (a plain element with `tabIndex={-1}`, as the page text in `Pagination` does). After a failure, focus goes back to the button. If the user moved focus somewhere else while the request ran, focus is left alone.
- **After the refresh.** The M41 recovery still runs. If the user is on `?status=completed&page=2` and clears completed todos, that page and the whole list become empty, the app moves to a valid page, and the normal empty message shows.
- A pure helper (`chooseClearCompleted`, `clearCompletedLabel`), one adapter method, one hook, one component, one flow, and the wiring in `TodoFlows`.
- Helper, adapter, hook, component, flow, and browser tests.

## Not included

- Any backend change. `DELETE /todos?status=completed` is already built and tested. If the evidence shows otherwise, I will stop and say so.
- A confirmation dialog or an undo. A bulk delete cannot be undone, and this is the main risk of the milestone. (See Risks.) The wording says `It cannot be undone`, and the single-todo Delete in this app also has no confirmation.
- Deleting only the visible page, the current filter, or the current search. The route accepts only `status=completed` and nothing else, so no partial scope exists.
- Deleting active todos or all todos.
- Blocking the row checkboxes, Edit, Delete, or the toggle-all control while the request runs. (See Risks.)
- Optimistic updates. The rows disappear only after the server answers and the list is refreshed.
- A router library, local storage, or any change to the URL. The control adds nothing to the URL.
- Changing how single delete moves focus. The bulk control has its own focus rule.

## Contracts

### Input

- A click, or Enter or Space on the focused button.
- The `completedCount` from the list response on screen.
- The adapter sends `DELETE /todos?status=completed` with no body and no `Content-Type` header. It sends no `search`, `page`, or `pageSize`, because the server refuses any other query key.

### Success

- `chooseClearCompleted(counts)` returns one of:
  - `{ kind: "none" }` when `completedCount` is 0.
  - `{ kind: "clear", count: completedCount }` when `completedCount` is above 0.
- The server returns `200` and `{ deletedCount }`. The hook returns `ok({ deletedCount })`.
- The flow refreshes every `["todos"]` key, shows `Deleted <deletedCount> completed todos.` (or `Deleted 1 completed todo.`), and moves focus to the status message if the button had focus before.
- If `deletedCount` is 0 (another tab already cleared them), the message is `There were no completed todos to delete.` and the list is refreshed.
- The label: `Clear all <completedCount> completed todos`, or `Clear the 1 completed todo` for one.
- Visibility and enabled state:

| Situation                                                             | The control                                      |
| --------------------------------------------------------------------- | ------------------------------------------------ |
| First load, no counts yet                                             | Nothing is shown                                 |
| Counts known, `completedCount` above 0                                | Button shown, enabled                            |
| Counts known, `completedCount` is 0, and no message                   | Nothing is shown                                 |
| Just cleared: `completedCount` is 0, and a success message is showing | Only the status message is shown, with no button |
| A new page, status, or search is loading, so no counts on screen      | Button shown with the last known count, disabled |
| The request is pending                                                | Button shown, really `disabled`                  |
| The list failed to load and there are no counts                       | Nothing is shown                                 |

### Expected failures

| Failure                                     | When it happens                                         | How it is represented                                                                                                   |
| ------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| NO_COMPLETED                                | `completedCount` is 0.                                  | The button is not rendered, so there is nothing to submit. If code calls the flow anyway, it returns without a request. |
| COUNTS_UNKNOWN                              | A new key is loading and there are no counts on screen. | The button is disabled, and the flow sends nothing.                                                                     |
| ALREADY_PENDING                             | A second click or key press while a request runs.       | The button is `disabled`, and a ref guard also refuses a second call. Only one request is sent.                         |
| API_ERROR (400)                             | The server refuses the query.                           | The safe failure message. It cannot happen with the fixed query, and a test pins the exact URL.                         |
| NETWORK_ERROR, API_ERROR (5xx), PARSE_ERROR | The request fails or the response cannot be read.       | The same safe failure message, `Could not clear completed todos. Please try again.`                                     |

### Unexpected failures

- A thrown error from the hook is not expected, because it returns a typed `Result`. If something throws anyway, the flow leaves the pending state so the button is never stuck disabled, and shows the safe failure message.
- Raw errors, status codes, and server messages are never shown.
- A refresh after success that fails shows the existing refresh-failure banner for the list. The success message still stands, because the delete itself worked.

## Certainty checks

**What information enters the system?**
A click or key press on the button, the counts from the list response, and the API response to `DELETE /todos?status=completed`.

**How will you check that information?**
The counts are numbers that already passed the list response schema. `chooseClearCompleted` decides from `completedCount` only. The adapter reads the `DELETE` response with `DeleteCompletedResponseSchema` before the app trusts `deletedCount`.

**What will the operation return when it succeeds?**
`ok({ deletedCount })`, then a refreshed list and refreshed counts in which no todo is completed, and every active todo is still there.

**What expected failures can happen?**
No completed todos, unknown counts, a second submission while pending, a refused query, a network or server error, and an unreadable response.

**How will each expected failure be represented?**
As values: the `none` choice, a disabled button, a `Result` error from the adapter, and a `failed` state in the flow. The code matches them with ts-pattern and `.exhaustive()`. Nothing expected throws.

**Where will the route, business rules, and database or UI work live?**
Route: none. Rules (when it shows, which words): the helper file. The fixed URL, fetch, and response checks: the adapter. Refresh after success: the hook. Pending, messages, and focus: the flow. Markup and accessibility: `ClearCompleted`. There is no database work in the web.

**What tests will you write before implementation?**
Listed below: helper, adapter, hook, component, flow, boundary, regression, and browser tests. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.

**How will you prove the whole operation works through its real boundaries?**
Playwright creates 45 todos through the real API and test database (20 completed, 25 active), goes to page 2 with a search, clicks the control, and checks the one `DELETE /todos?status=completed` request, the request count, and that all 20 completed todos are gone from every page while all 25 active todos remain. It also holds the response to check the pending state, fails the request to check the failure state, and runs a keyboard smoke test for focus.

**Does this change multiple records or call another system? If yes, how will failure be handled safely?**
Yes. It deletes every completed todo with one `DELETE ... RETURNING` statement on the server, which is atomic: either every completed row is removed or none. A failure shows the safe message, leaves the list as it was, and lets the user try again. Deleted todos cannot be brought back, so the wording says so.

**If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?**

- Loading: no counts yet, so nothing is shown. While a new page or filter loads, the button shows the last known count and is disabled.
- Empty: no completed todos, so no button.
- Ready: the button with the full-collection label, and the help text.
- Pending: the button is `disabled`, the wrapper has `aria-busy="true"`, and the status line says `Clearing completed todos…`.
- Success: a polite status message (`role="status"`) with the number of todos deleted. It stays until the next action or until the page, status, search, or page size changes.
- Error: the safe message in an `alert`. The button is enabled again.
- Accessibility: a real `button` with the label as its visible text and name. `aria-describedby` points to the help text. Enter and Space work, because it is a native button. A visible focus ring. It sits after the list and before the page bar in the tab order. After a success, focus goes to the status message (a plain element with `tabIndex={-1}`), because the button is gone. After a failure, focus goes back to the button. The status and alert boxes are always on the page while the control is shown, because a screen reader only reads a live region that was already there before its text changed.

## Risks and assumptions

- **A delete that cannot be undone.** Every completed todo on every page is removed, and there is no confirmation and no undo in this milestone. The wording says `Clear all 20 completed todos` and `It cannot be undone`, so the user is told before they click. If the reviewer wants a confirmation step, it is a new milestone, and it would change tests 23 to 25, 35, and 58.
- **Hidden and not disabled.** "Unavailable" is read as "not on the page". A hidden button cannot be focused or pressed. If the reviewer wants a visible disabled button instead, only `buttonVisible` and tests 26, 33, and 57 change.
- **Counts and the search.** The label's number comes from `completedCount`. If it follows the search, the number would be wrong while a search is active. Test 56 checks this, and the plan stops there if it fails.
- **Stale counts.** The number the user sees may be a moment old, because another tab can complete or delete todos. The server deletes whatever is completed at that moment, and the message uses the server's `deletedCount`, so the user is told the real number. Test 67 covers the zero case.
- **Focus is lost when the button goes away.** After a success there are no completed todos, so the button leaves the page. The flow moves focus to the status message first, even before the counts refresh, because waiting for the refresh would lose focus. Tests 44 to 47 and 65 check this.
- **Two focus owners.** `useTodoDeleteFlow` also moves focus after a single delete. It only acts on ids it deleted, so it does nothing for a bulk clear. Test 52 proves this.
- **Double submission.** The `disabled` attribute and the ref guard both stop it, because a fast second click can arrive before React re-renders. Tests 38 and 63 check this.
- **Stuck pending.** If anything throws, the flow leaves the pending state. Test 43 checks this.
- **Other bulk and row actions during the request.** A single-row toggle, edit, or delete, or the toggle-all control, started during the bulk delete can finish before or after it. The final refresh shows the server's real state, so the screen is never wrong for long. I will not block them in this milestone, as in M44. A row that is deleted by the bulk request while the user edits it ends in the existing 404 handling.
- **Late refresh.** After the delete, a refresh for the current key is requested. Other keys are marked stale and load when they are opened. The list has no `placeholderData`, so an old response cannot replace the current list.
- **Filtered list becomes empty.** Clearing under Completed empties the list. The M41 recovery handles an empty page past the range, and the normal empty message handles page 1. Test 62 checks this.
- **No axe library.** Component accessibility is checked by hand, as in M44, with test 31.
