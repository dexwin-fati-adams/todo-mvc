Objective
Plan explicit selection without confusing selection with completion.
Included

- Entry and exit are explicit. A "Select todos" button above the list turns selection mode on. A "Done selecting" button turns it off. Nothing else turns it on or off: not a page change, not a filter change, not a search. Exiting clears the selection.
- Separate checkboxes. In selection mode every row gets a second checkbox, named Select “Buy milk”. The existing completion checkbox keeps its name (Buy milk) and its behaviour. Clicking one never changes the other. Selecting sends no request at all.
- Select visible page. One button, Select all 20 todos on this page, selects the todos on screen, in page order, skipping ones already selected. It is the only "select many" control. There is no "select everything that matches".
- Clear selection. A Clear selection button empties the selection and keeps selection mode on.
- Selected count. A status line always shows 3 of 100 selected. At the limit it says 100 of 100 selected. Limit reached.
- 100-item limit. The reducer enforces SELECTION_LIMIT = 100, so no UI path can go past it.
  - At the limit, unselected row checkboxes are really disabled. Selected ones stay enabled, so the user can unselect.
  - If Select all N todos on this page would pass the limit, it selects as many as fit, in page order, and the status line says You can select up to 100 todos. 10 todos were not selected.
  - When the limit is already reached, Select all N todos on this page is disabled.
- Query-scoped persistence. The selection belongs to one scope: JSON.stringify([status, search]). The page and the page size are not part of the scope.
  - Changing page keeps the selection.
  - Changing page size keeps the selection.
  - Returning to a page shows its rows still checked.
  - The selection lives in memory only. A reload clears it and turns selection mode off.
- Clearing rules. The selection is cleared when:
  1. the status changes,
  2. the committed search changes or is cleared,
  3. the user presses Clear selection,
  4. the user presses Done selecting.
- When the status or search changes, selection mode stays on, the selection is emptied, and the status line says Selection cleared because the status or search changed. Going back to an earlier scope does not bring the old selection back. A selected todo that the user deletes from its row is removed from the selection.
- Hidden standard batch controls. While selection mode is on, ToggleAll and ClearCompleted are not rendered. They come back when the user exits. Their flows keep running, because hooks cannot be called conditionally, so a message from a request that finished meanwhile shows when the controls return.
- Reducer. A pure selectionReducer owns every rule. States, actions, and results are listed under Contracts. It uses ts-pattern with .exhaustive().
- Labels, help text, and messages. Exact wording is listed under Contracts. All wording comes from pure functions in selectionLabels.ts, so a test pins each sentence.
- Focus. Listed under Contracts. A control that disables itself never leaves keyboard focus on body.
- Live regions. The count line is the only live region, and it exists only in selection mode. There is no empty role="alert" or role="status" anywhere. (This is the M44 lesson: permanent empty regions broke an existing Playwright assertion.)
- Tests: reducer, labels, component, row, flow, TodoFlows, boundary, regression, and browser tests.
  Not included
- Any action on the selected todos (complete, delete, and so on). That is a later milestone. This milestone only builds the selection.
- Any backend change. Selection is client-only. A browser test proves that selecting sends no request.
- Selecting every todo that matches the query, across pages. Only the visible page can be selected in one step.
- Saving the selection in the URL, local storage, or session storage.
- Shift-click range selection, keyboard shortcuts, and Escape to exit.
- Hiding the completion checkbox, Edit, or Delete during selection mode.
- Checking that selected ids still exist on the server. (See Risks.)
- A confirmation dialog.
- Changing the status filter, search, or pagination components.

type SelectionNotice =
| { kind: "limit"; skipped: number }
| { kind: "scope-cleared" }
| { kind: "cleared" };

type SelectionState =
| { mode: "off" }
| {
mode: "on";
scopeKey: string;
selected: readonly string[]; // ids, in the order they were selected, no duplicates
notice: SelectionNotice | null;

type SelectionAction =
| { type: "enter"; scopeKey: string }
| { type: "exit" }
| { type: "toggle"; id: string }
| { type: "selectVisible"; ids: readonly string[] }
| { type: "clear" }
| { type: "scopeChanged"; scopeKey: string }

Unexpected failures

- Nothing here calls the network, so there is no request to fail. The reducer is total: every action and state is matched with .exhaustive(), so an unhandled action is a compile error and not a runtime throw.
- If a row id is missing from the list when a click arrives (for example, the list refreshed), toggle treats it like any other id. No lookup can throw.
- Raw ids are never shown to the user. Only the todo title appears, as text.

  Certainty checks
  What information enters the system? Clicks and key presses on the selection controls, the status and committed search from the page address, the ids of the rows on screen, and the id of a deleted row.
  How will you check that information? The ids come from the list response, which already passed its schema. The scope key is built from values that useListParams already validated (parseStatus, parseSearch). The reducer ignores duplicates, enforces the limit, and ignores actions that do not apply to the current mode.
  What will the operation return when it succeeds? A new SelectionState (or the same reference when nothing changes). The view shows the new count, the checked rows, and a notice if there is one.
  What expected failures can happen? The limit, nothing to select, everything already selected, a scope change, and an action while mode is off.
  How will each expected failure be represented? As values: notice in the state, a disabled control, or the same state returned. The code matches them with ts-pattern and .exhaustive(). Nothing expected throws.
  Where will the route, business rules, and database or UI work live? Route: none. Rules (limit, scope, clearing): selectionReducer.ts. Words: selectionLabels.ts. State, scope tracking, and focus: useSelectionFlow. Markup and accessibility: SelectionControls and SelectionCheckbox. There is no database work.
  What tests will you write before implementation? Listed below: reducer, labels, component, row, flow, TodoFlows, boundary, regression, and browser tests. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.
  How will you prove the whole operation works through its real boundaries? Playwright creates todos through the real API and test database, enters selection mode, selects a page, changes page, status, search, and page size, hits the limit with 120 todos, exits, and reloads. It records every request the browser makes to the API and checks that selecting sent none.
  Does this change multiple records or call another system? If yes, how will failure be handled safely? No. It changes only in-memory state in the browser. There is no failure to handle, and a browser test checks that no request is sent.
  If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?
- Loading: while the first response for a key loads, the entry button is shown but disabled. In selection mode the toolbar stays, and Select all… is disabled because there are no rows.
- Empty: the entry button is not shown when there is nothing to select. In selection mode with no rows, the toolbar stays so the user can clear or exit.
- Ready: the entry button, or the toolbar with the count line and one selection checkbox per row.
- Error: a failed list load shows the existing list error. The selection is untouched, because it holds ids and not data from the failed response. The toolbar stays usable.
- Pending: no request exists, so there is no pending state for selection. A bulk request started earlier by ToggleAll or ClearCompleted may still be running when the user enters selection mode. The controls are hidden and their message shows when they return. (See Risks.)
- Accessibility: real input type="checkbox" elements with real labels. The toolbar is a role="group" named Selection mode and described by the help text. The count line is the only live region (role="status", polite), with tabIndex={-1} as a focus target. Checked state is the native check mark, not colour. Disabled checkboxes at the limit use the real disabled attribute, and the reason is in the count line. Every button and checkbox has the visible focus ring used elsewhere. The new buttons are in the tab order after the search box and status links, before the list.

     Risks and assumptions

- Selection and completion get confused. A user may think a ticked selection box means "done". The rows have two checkboxes with different names, the toolbar help text says selecting does not change completion, and a browser test checks both directions (test 87).
- Stale ids. The selection holds ids, not todos. A todo deleted in another tab stays in the selection, and the count is then one too high. Nothing is sent in this milestone, so nothing breaks. The milestone that acts on the selection must handle ids that no longer exist (a 404) and must refresh before it acts. I will note this in the pull request.
