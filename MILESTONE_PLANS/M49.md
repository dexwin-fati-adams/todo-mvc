## Objective

Plan the full-stack operation that marks specific todos complete or active.

## Included

**Backend**

- **One new route: `PATCH /todos/batch`.** Request body `{ "ids": string[], "completed": boolean }`. Success is `200` with `{ "updatedCount": number }`.
- **Validation (`400`, `VALIDATION_ERROR`, nothing changed).** `ids` must be an array of 1 to 100 unique UUIDs. `completed` must be a boolean. Any other field is refused (`.strict()`). Rejected: empty `ids`, duplicates, an invalid id, 101 ids, a missing or non-boolean `completed`, an unknown field, and an empty or unreadable body.
- **Atomic.** The whole update runs in one transaction. Either every listed todo changes or none does.
- **Missing id conflict (`409`, `batch_conflict`, nothing changed).** If any id does not exist, the transaction rolls back and the response lists the missing ids, so the web can recover. A todo deleted a moment earlier is a conflict like any other.
- **`updatedCount`** is the number of todos in the request, all of which were found. A todo that already had the requested value still counts, because it was found and set.
- **Route order.** `/todos/batch` is a fixed path and `/todos/:id` takes a parameter. The batch route must win. A test pins this, because `batch` would otherwise be read as a bad id.
- No change to `PATCH /todos`, `PATCH /todos/:id`, `POST /todos/toggle-all`, or `DELETE /todos`.

**Frontend**

- **Two buttons in the selection toolbar:** `Mark N selected todos as complete` and `Mark N selected todos as active`. The user chooses the direction. Nothing is chosen from the counts, because selection is explicit.
- **Ids come only from the selection.** Never from the rows on screen, so a selection across pages is sent whole.
- **Pessimistic.** The rows and counts change only after the server answers and the list is refreshed. There is no optimistic update.
- **Pending.** Both buttons are really `disabled`, a ref guard refuses a second call, the status line says `Updating N selected todos…`, and the toolbar is `aria-busy`. While the request runs, the selection is locked: the row selection checkboxes, `Select all…`, `Clear selection`, and `Done selecting` do nothing, so nothing can change what the success will clear.
- **Success.** Every `["todos"]` query is refreshed, the selection is cleared, selection mode stays on, and the status line says `Marked N selected todos as complete.` (or `as active.`) with the server's `updatedCount`.
- **Conflict.** The ids named as missing are removed from the selection, the list is refreshed, and the status line says `Nothing was changed. 2 selected todos no longer exist and were removed from the selection.` The remaining selection is kept and the buttons are enabled, so the user can press the button again. There is no automatic retry.
- **Failure (network, `5xx`, unreadable answer, or an unexpected `400`).** A safe message in an alert: `Could not update the selected todos. Please try again.` The selection is kept, the buttons are enabled, and the user can retry. No status code or server text is shown. Retrying is safe, because the request sets an absolute value.
- **Typed errors, no new case in `ClientError`.** The adapter returns its own error union (`ClientError` plus a `BATCH_CONFLICT` case with `missingIds`). The existing exhaustive matches on `ClientError` stay untouched.
- **One live region.** Messages for pending, success, and conflict go through the single status line. The failure alert exists only while there is a failure. There is no empty `role="alert"` or `role="status"` anywhere (the M44 lesson).
- Tests: contract, service, integration, adapter, hook, reducer, labels, component, flow, `TodoFlows`, boundary, regression, and browser tests.

## Not included

- Deleting selected todos, or any other action on the selection. Those are later milestones.
- Partial success. The operation is all or nothing.
- Optimistic updates, undo, a confirmation dialog, or an automatic retry after a conflict.
- Changing only part of a selection that spans more than 100 todos. The selection limit is already 100.
- Per-id error details beyond the missing ids.
- Blocking the single-row completion checkboxes, Edit, or Delete while the batch request runs. (See Risks.)
- A new database table, a migration, or any change to the existing routes.
- Server-side limits other than the 1 to 100 ids rule.

## Contracts

### Input

- **API request:** `PATCH /todos/batch` with a JSON body `{ "ids": string[], "completed": boolean }`. No query string. This is the exact contract to be confirmed against the requirements document in step 1.
  - `ids`: an array of 1 to 100 items, each a UUID, all different.
  - `completed`: a boolean.
  - No other field.
- **UI:** a click, Enter, or Space on one of the two action buttons. The ids are the current selection, in the order they were selected.

### Success

- **API:** `200` with `{ "updatedCount": <number of ids> }`. Every listed todo now has the requested `completed` value. No other todo changed.
- **Web adapter:** `ok({ updatedCount })`.
- **Hook:** `update(ids, completed)` returns the adapter's `Result` and, on success, refreshes every `["todos"]` key.
- **Flow:** the selection is cleared (`updated` action), mode stays on, and the status line shows `Marked <updatedCount> selected todos as complete.` The buttons are then disabled because nothing is selected.

### Messages and labels (all from pure functions in `selectionLabels.ts`)

| What            | Text                                                                                                                                                                            |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Complete button | `Mark 3 selected todos as complete` (singular: `Mark 1 selected todo as complete`)                                                                                              |
| Active button   | `Mark 3 selected todos as active` (singular: `Mark 1 selected todo as active`)                                                                                                  |
| Pending         | `Updating 3 selected todos…` (singular: `Updating 1 selected todo…`)                                                                                                            |
| Success         | `Marked 3 selected todos as complete.` / `Marked 3 selected todos as active.` (singular: `Marked 1 selected todo as complete.`)                                                 |
| Conflict        | `Nothing was changed. 2 selected todos no longer exist and were removed from the selection.` (singular: `1 selected todo no longer exists and was removed from the selection.`) |
| Failure (alert) | `Could not update the selected todos. Please try again.`                                                                                                                        |
| Help text       | `Changes only the selected todos, on every page.`                                                                                                                               |

The success and conflict messages are notices in the reducer, so they follow the existing rule that a notice shows once and is replaced by the next change. The count line shows the count first and then the notice, as before.

### Reducer additions

```ts
type SelectionNotice =
  | { kind: "limit"; skipped: number }
  | { kind: "scope-cleared" }
  | { kind: "cleared" }
  | { kind: "updated"; count: number; completed: boolean }   // new
  | { kind: "conflict"; removed: number };                   // new

type SelectionAction =
  | /* the existing seven actions */
  | { type: "updated"; count: number; completed: boolean }   // new
  | { type: "conflict"; missingIds: readonly string[] };     // new
```

| Action     | In `off`   | In `on`                                                                                                                                                                                                      |
| ---------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `updated`  | Same state | `selected: []`, notice `updated`, same scope key                                                                                                                                                             |
| `conflict` | Same state | Remove only the ids that are both selected and named as missing, keep the order of the rest, and set notice `conflict` with the number removed. If none of the named ids is selected, return the same state. |

A failure does not touch the reducer: the selection stays as it was.

### Visibility and enabled state (selection toolbar)

| Situation                 | Action buttons                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Mode off                  | Not rendered                                                                                                                   |
| Mode on, nothing selected | Shown, really `disabled`                                                                                                       |
| Mode on, N selected       | Shown, enabled                                                                                                                 |
| Request pending           | Shown, really `disabled`. `Select all…`, `Clear selection`, `Done selecting`, and the row selection checkboxes are also inert. |
| After success             | Shown, disabled (nothing selected)                                                                                             |
| After conflict            | Shown, enabled if ids remain, disabled if none remain                                                                          |
| After failure             | Shown, enabled                                                                                                                 |

### Focus

| Event                                                      | Where focus goes                                                   |
| ---------------------------------------------------------- | ------------------------------------------------------------------ |
| Press an action button (it becomes disabled while pending) | Stays where it is until the request ends                           |
| Request ends in success                                    | The count line (nothing is selected, so both buttons are disabled) |
| Request ends in conflict, and the buttons are enabled      | The button the user pressed                                        |
| Request ends in conflict, and no ids remain                | The count line                                                     |
| Request ends in failure                                    | The button the user pressed                                        |

Focus moves only if it was on the pressed button or on `body`. If the user moved somewhere else, it is left alone. An action that sends no request (nothing selected) stores no focus plan.

### Expected failures

| Failure                                                            | When it happens                                | How it is represented                                                                                                                                                                                                                              |
| ------------------------------------------------------------------ | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| VALIDATION (`400`)                                                 | The body breaks the contract                   | API: `400` `VALIDATION_ERROR`, nothing changed. Web: cannot happen from the UI (the reducer enforces 1 to 100 unique ids, and the adapter checks the same schema first). A test pins the body. If it ever happens, the safe failure message shows. |
| BATCH_CONFLICT (`409`)                                             | One or more ids do not exist                   | API: `409` `batch_conflict` with the missing ids, nothing changed. Web: `BATCH_CONFLICT` with `missingIds`, then the conflict recovery.                                                                                                            |
| NOTHING_SELECTED                                                   | Zero ids                                       | The buttons are disabled. If code calls the flow anyway, it returns without a request.                                                                                                                                                             |
| ALREADY_PENDING                                                    | A second click while a request runs            | The buttons are `disabled` and a ref guard also refuses the call. ### Unexpected failures

- A thrown error from the adapter is not expected, because it returns a typed `Result`. If something throws anyway, the flow leaves the pending state in a `finally` and shows the safe failure message.
- The server never returns a stack trace or SQL in an error body. A test checks that.
- Raw errors, status codes, and server text are never shown.
- A refresh after success that fails shows the existing refresh-failure banner for the list. The success message still stands, because the update itself worked.
- If the user changes the status or the search while the request runs, the reducer clears the selection (the M48 rule). The result is still reported, and an old selection is never brought back.

## Certainty checks

**What information enters the system?**
The ids and the boolean in the request, and in the web a click on one of the two buttons and the current selection.

**How will you check that information?**
The server checks the body with `UpdateBatchRequestSchema` (1 to 100 unique UUIDs, a boolean, no other field) before anything runs. The web reducer already enforces the limit and uniqueness, the adapter checks the same schema before it sends, and the server checks again. The adapter reads every answer with a schema before the app trusts `updatedCount` or `missingIds`.

**What will the operation return when it succeeds?**
`200` with `{ updatedCount }`, equal to the number of ids, with every listed todo set to the requested value. In the web, `ok({ updatedCount })`, then a refreshed list and an empty selection.

**What expected failures can happen?**
Invalid input (`400`), missing ids (`409`), a second click while pending, nothing selected, and a network, server, or unreadable-answer failure.

**How will each expected failure be represented?**
As values: `VALIDATION_ERROR`, `batch_conflict` with `missingIds`, a typed `Result` error in the adapter, and a notice or a failure state in the web flow. The code matches them with ts-pattern and `.exhaustive()`. Nothing expected throws.

**Where will the route, business rules, and database or UI work live?**
Route: the new route file. Rules (1 to 100 unique ids, all-or-nothing, which ids are missing): the contract schema and the service. Database work: one statement in a transaction in the data access layer. Fetch and answer checks: the adapter. Refresh: the hook. Pending, lock, messages, and focus: the flow and the reducer. Markup and accessibility: `SelectionControls`.

**What tests will you write before implementation?**
Listed below. Each starts from a placeholder, so it fails on a missing behaviour and not on a broken import.

**How will you prove the whole operation works through its real boundaries?**
Integration tests call the real route against the real test database, including a conflict that leaves the other rows unchanged. Playwright creates todos through the real API, selects them across pages, clicks a button, records the one `PATCH /todos/batch` request and its exact body, and checks the rows, the counts, the selection, and the API. It also holds the response to check the pending state, fails the request to check the failure state, and deletes a selected todo first to check the conflict recovery.

**Does this change multiple records or call another system? If yes, how will failure be handled safely?**
Yes, it changes up to 100 records. It runs in one transaction, so it is all or nothing. A conflict rolls everything back and returns the missing ids. A failure shows a safe message, leaves the selection and the list as they were, and the user can retry. Retrying is safe because the request sets an absolute value.

**If this is frontend work, what loading, empty, ready, error, pending, and accessibility states are needed?**

- Loading: the action buttons depend only on the selection count, so they are not affected by a list that is loading.
- Empty: nothing selected, so both buttons are disabled.
- Ready: two buttons that name the direction and the number of todos, and the help text.
- Pending: both buttons really `disabled`, the toolbar `aria-busy`, the status line `Updating N selected todos…`, and the selection locked.
- Success: the status line with the number changed. It stays until the next action.
- Conflict: the status line says nothing was changed and how many ids were removed. The buttons are enabled for a retry.
- Error: the alert with the safe message, which exists only while the failure is on screen. The selection is kept.
- Accessibility: real buttons with visible text names, a visible focus ring, the single live region, an alert only on failure, focus handled as in the Focus table, and tab order after `Select all…`, before `Clear selection` is not required to change the existing order, so the two new buttons follow `Select all…`.

## Risks and assumptions

- **Contract details come from the requirements document.** The field names, the `409` body, and the lower-case `batch_conflict` code are assumptions until step 1. If the document gives a `409` body without the missing ids, recovery cannot work as planned, and I will stop and ask.
- **Error code casing.** `batch_conflict` is lower case and the existing `VALIDATION_ERROR` is upper case. I will follow the requirement and note the mismatch in the pull request.
- **Route order.** `/todos/batch` against `/todos/:id` must resolve to the batch route. A test pins it, and a second test pins that the old routes did not change.
- **`updatedCount` meaning.** It counts todos found and set, including ones that already had the value. This must match how `PATCH /todos` counts, and step 1 checks it.
- **Lost answer.** If the network fails after the server applied the change, the list is stale until the next refresh. Retrying is safe because the value is absolute. I chose not to refresh after a network failure, because a refresh while offline would only add a second error.
- **Selection lock.** The selection is locked while the request runs, so that clearing it on success cannot throw away new picks. This adds inert controls during the request, which tests 71 and 82 cover.
- **Row actions during the request.** A single-row completion toggle, Edit, or Delete started while the batch request runs can finish before or after it. The final refresh shows the server's real state, so the screen is never wrong for long. I will not block them in this milestone.
- **Stale ids that are not missing.** A todo can be edited or deleted elsewhere between selection and click. Deleted ones are handled by the conflict. A todo that only changed is simply set to the requested value, which is what the user asked for.
- **Large requests.** 100 ids is small for one `UPDATE … WHERE id = ANY(…)`. Test 21 and test 99 cover it.
- **Conflict wording.** `Nothing was changed.` is true for a `409`, because the transaction rolled back. It is not used for a network failure, where the outcome is unknown.
- **Tab stops and live regions.** The new buttons add tab stops, so every keyboard test loops until the target has focus. The status line stays the only live region.
- **`QueryClient` mocks.** The new hook needs a mock in every test file that renders `TodoFlows`. I will find them in step 1.
- **Letter case in file names.** A wrong case passes on macOS and fails in CI on Linux. I will run `git grep` before every push.
- **Local Playwright.** It did not start earlier because the database was not ready. If that is still true, CI is the reliable browser result, and I will say so.
- Ports. The apps use 4000 and 4001.
- Assumes no login is needed, because the project has no auth yet.
