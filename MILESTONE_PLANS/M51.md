## Objective

Plan the full-stack operation that deletes specific todos.

## Included

**Backend**

- **One new route: `POST /todos/batch-delete`.** Request body `{ "ids": string[] }`. Success is `200` with `{ "deletedCount": number }`.
- **Validation (`400`, `VALIDATION_ERROR`, nothing deleted).** `ids` must be an array of 1 to 100 unique UUIDs. Any other field is refused (`.strict()`). Rejected: empty `ids`, duplicates, an invalid id, 101 ids, a missing `ids`, an unknown field, and an empty or unreadable body. The limit reuses `BATCH_MAX_IDS` from M50.
- **Atomic.** One transaction. Either every listed todo is deleted or none is.
- **Missing id conflict (`409`, `batch_conflict`, nothing deleted).** If any id does not exist, the transaction rolls back and the response lists the missing ids. The body is the existing `BatchConflictResponseSchema`. A todo deleted a moment earlier is a conflict like any other.
- **`deletedCount`** is the number of ids in the request, all of which were found and deleted.
- **Route order.** `POST /todos/batch-delete` and `POST /todos/toggle-all` are both fixed paths and there is no `POST /todos/:id`, so there is no clash. A test pins that `toggle-all` still works.
- No change to `DELETE /todos/:id`, `DELETE /todos?status=completed`, `PATCH /todos/batch`, or any other existing route.

**Frontend**

- **One new button in the selection toolbar:** `Delete N selected todos`. Help text under it: `Deleting cannot be undone.`
- **Confirmation (inline, two steps).** Pressing the button does not send anything. It shows `Delete N selected todos? This cannot be undone.` with two buttons: `Yes, delete N todos` and `Cancel`. Only the confirm button sends the request. Decision to confirm with the manager (see Risks).
- **Ids come only from the selection.** Never from the rows on screen, so a selection across pages is sent whole.
- **Pessimistic.** Rows and counts change only after the server answers and the list is refreshed. There is no optimistic removal.
- **Pending.** All batch buttons (update and delete) are really `disabled`, a ref guard refuses a second call, the status line says `Deleting N selected todos…`, the toolbar is `aria-busy`, and the selection is locked exactly as in M50. Update and delete share one pending lock, so only one batch operation runs at a time.
- **Success.** Every `["todos"]` query is refreshed, the selection is cleared, selection mode stays on, and the status line says `Deleted N selected todos.` with the server's `deletedCount`. If the current page becomes empty, the existing out-of-range recovery applies.
- **Conflict.** The ids named as missing are removed from the selection, the list is refreshed, and the status line says `Nothing was deleted. 2 selected todos no longer exist and were removed from the selection.` The remaining selection is kept and the buttons are enabled. There is no automatic retry. The confirmation closes.
- **Failure (network, `5xx`, unreadable answer, or an unexpected `400`).** A safe message in an alert: `Could not delete the selected todos. Please try again.` The selection is kept, the buttons are enabled, and the user can retry. No status code or server text is shown. Retrying is safe: a todo already deleted by the first attempt turns the retry into a conflict, which the conflict recovery handles.
- **Stale alert.** The failure state is cleared on scope change, enter, exit, clear and when the next request starts (the M50 review lesson F1).
- **Typed errors, no new case in `ClientError`.** The adapter reuses `UpdateBatchError`'s shape: `ClientError` plus `BATCH_CONFLICT` with `missingIds`.
- **One live region.** Pending, success and conflict go through the single status line. The failure alert exists only while there is a failure. No empty `role="alert"` or `role="status"`.
- Tests: contract (through integration), service, repository, integration, adapter, hook, reducer, labels, component, flow, `TodoFlows`, and browser tests.

## Not included

- Deleting by status or search, undo, soft delete, or restore.
- Partial success. The operation is all or nothing.
- Optimistic removal or an automatic retry after a conflict.
- Selections over 100 todos. The selection limit is already 100.
- Per-id error details beyond the missing ids.
- Blocking the single-row checkboxes, Edit or Delete while the batch request runs (same decision as M50).
- A new table, a migration, or any change to existing routes.
- Changing CI. (Noted as a risk: CI does not type-check `apps/web`.)

## Contracts

### Input

- **API request:** `POST /todos/batch-delete` with JSON `{ "ids": string[] }`. No query string.
  - `ids`: 1 to 100 items, each a UUID, all different. No other field.
- **UI:** a click on `Delete N selected todos`, then a click on `Yes, delete N todos`. The ids are the current selection, in selection order.

### Success

- **API:** `200` with `{ "deletedCount": <number of ids> }`. Every listed todo is gone. No other todo changed.
- **Web adapter:** `ok({ deletedCount })`. **Hook:** `remove(ids)` returns the adapter's `Result` and, on success and on conflict, refreshes every `["todos"]` key.
- **Flow:** selection cleared (`deleted` action), mode stays on, status line `Deleted <deletedCount> selected todos.`

### Reducer additions

```ts
type SelectionNotice =
  | /* existing */
  | { kind: "deleted"; count: number }                 // new
  | { kind: "delete-conflict"; removed: number };      // new

type SelectionAction =
  | /* existing */
  | { type: "deleted"; count: number }                 // new
  | { type: "deleteConflict"; missingIds: readonly string[] }; // new
```

| Action           | In `off`   | In `on`                                                                                                                                             |
| ---------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deleted`        | Same state | `selected: []`, notice `deleted`, same scope key                                                                                                    |
| `deleteConflict` | Same state | Remove only ids that are selected and named missing, keep order, notice `delete-conflict` with the number removed. If none is selected, same state. |

The confirmation is local UI state in the flow, not in the reducer. It closes on cancel, on scope change, on enter, on exit, on clear, on any selection change, and when the request starts.

| ----------------------------------- | ------------------------------------------------------------- |
| Press `Delete N selected todos`     | The confirm button (so Enter confirms and Tab reaches Cancel) |

### Expected failures

| Failure                                                | How it is represented                                                                                                                                                                                      |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| VALIDATION (`400`)                                     | API: `400 VALIDATION_ERROR`, nothing deleted. Web: cannot happen from the UI (the reducer enforces the limit and the adapter checks the same schema first). If it happens, the safe failure message shows. |
| BATCH_CONFLICT (`409`)                                 | API: `409 batch_conflict` with `missingIds`, nothing deleted. Web: `BATCH_CONFLICT`, then conflict recovery.                                                                                               |
| NOTHING_SELECTED                                       | The buttons are disabled. If code calls the flow anyway, no request is sent.                                                                                                                               |
| ALREADY_PENDING                                        | Buttons `disabled` and a ref guard. One request is sent.                                                                                                                                                   |
| NETWORK_ERROR, API_ERROR (`5xx` or other), PARSE_ERROR | Safe failure message in an alert. Selection kept.                                                                                                                                                          |
| CONFLICT_BODY_UNREADABLE                               | `API_ERROR` status `409`, so the safe failure message shows.                                                                                                                                               |

### Unexpected failures

- A thrown error from the hook is not expected. If one happens, the flow leaves pending in a `finally` and shows the safe failure message.
- The server never returns a stack trace or SQL in an error body. A test checks that.
- If the refresh after success fails, the existing refresh-failure banner shows. The success message still stands, because the delete worked.
- If the status or search changes while the request runs, the reducer clears the selection. The result is still reported and an old selection is never brought back.

## Responsibilities

| Layer              | Responsibility                                                                                                                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Contracts          | `DeleteBatchRequestSchema` (`ids` 1 to `BATCH_MAX_IDS` unique UUIDs, `.strict()`) and `DeleteBatchResponseSchema` (`deletedCount`). The conflict schema is reused.                                                                               |
| Route              | `POST /todos/batch-delete`: validate, call the service, map `ok` to `200`, `conflict` to `409 batch_conflict`, validation to `400`.                                                                                                              |
| Service            | `deleteBatch(ids)` delegates to the repository. Matches the result with ts-pattern `.exhaustive()` in the route.                                                                                                                                 |
| Repository         | One transaction: `DELETE FROM todos WHERE id = ANY($1) RETURNING id`. Compare with the requested ids. If any is missing, `rollback()` and return `conflict` with `missingIds` in request order. Database failures become `TODO_DB_ERROR` values. |
| Adapter            | `todoApi.deleteBatch({ ids })`: check with the schema first (no request if invalid), `POST /todos/batch-delete`, read `200` with the response schema, read `409` with the conflict schema. Never throws.                                         |
| Hook               | `useDeleteSelected()` returns `{ remove(ids), refresh() }`. The mutation function is `async` and returns the `Result`. Refresh on success and on conflict only.                                                                                  |
| Reducer and labels | The two actions and notices, and the new sentences. Pure.                                                                                                                                                                                        |
| Flow               | Shared pending lock, confirmation state, `onDelete`, `onConfirmDelete`, `onCancelDelete`, conflict and failure handling, focus plans.                                                                                                            |
| View               | `SelectionControls` draws the delete button, the confirmation and the alert from props. No rules.                                                                                                                                                |

## Certainty checks

**What information enters the system?** The ids in the request, and in the web two clicks (delete, then confirm) plus the current selection.

**How will you check it?** The server checks the body with `DeleteBatchRequestSchema` before anything runs. The reducer enforces the limit, the adapter checks the same schema, the server checks again. The adapter reads every answer with a schema before trusting `deletedCount` or `missingIds`.

**What does it return on success?** `200 { deletedCount }`. In the web, `ok({ deletedCount })`, a refreshed list and an empty selection.

**What expected failures can happen?** Invalid input, missing ids, a second click while pending, nothing selected, network or server failure.

**How are they represented?** As values. Nothing expected throws.

**Where do the rules live?** Validation and conflict in the contract and the repository. Pending, confirmation, messages and focus in the flow and reducer. Markup in `SelectionControls`.

**Does it change multiple records?** Yes, up to 100 deletions, in one transaction. A conflict rolls everything back.

**Frontend states:** loading (buttons depend only on the selection), empty (disabled), ready, confirming, pending, success, conflict, failure alert, and accessibility as in the Focus table. Real buttons with visible names, visible focus ring, one live region.

## Risks and assumptions

- **Confirmation.** The plan adds an inline confirmation for an irreversible action. M49 had none for completion. If the manager does not want it, the Confirmation rows, tests 32, 33, 39 and 65 are removed and the delete button sends directly.
- **Shared pending lock.** Update and delete share one lock. Changing the update names in `useSelectionFlow` must not break the M50 tests, so the rename is its own commit with all tests green.
- **Lost answer.** If the network fails after the server deleted the rows, the list is stale until the next refresh and a retry returns a conflict listing every id. The conflict recovery handles it and the message is accurate (`Nothing was deleted` is true for that response). I do not refresh after a network failure.
- **Concurrent deletes.** Two overlapping requests for the same ids: the second finds the rows already deleted, so it returns a conflict and deletes nothing. Test 11 covers the sequential case.
- **Row actions during the request.** A single-row Edit or Delete started while the batch runs can finish before or after it. The final refresh shows the real state. Not blocked in this milestone.
- **Page recovery.** Deleting every row of the last page relies on the existing recovery. Browser test 73 covers it.
- **`apps/web` is not type-checked by CI.** I run `tsc --noEmit` in `apps/web` myself. Fixing CI is a separate change.
- **Dev database.** If step 1 shows the API tests hit the dev database, I will not run them until it is fixed or the manager says it is acceptable.
- **Local Playwright.** It needs the test database to have the schema. I apply the migration by hand if `\dt` is empty, and say so in the pull request.
- Ports: the apps use 4000 and 4001. No login is needed, because the project has no auth yet.
